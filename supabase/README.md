# ОРБИТА 3Б — подготовленная серверная схема

Миграция **не применена в облаке**. Основной документ — [пакет на одобрение](../docs/STAGE_3B_APPROVAL_PACKAGE.md). Папка не содержит конфигурации связанного облачного Supabase и не запускает `supabase db push`.

- `migrations/202611050001_stage3b_auth.sql` — одна транзакция для нового согласованного проекта. При существующих объектах останавливается.
- `admin/01_provision_profile.sql` — доверенный профиль без роли.
- `admin/02_bootstrap_admin.sql` — отдельное назначение первого администратора.
- `admin/03_change_access.sql` — одна операция assign/revoke/block/unblock над одним UUID.
- `tests/bootstrap_local.sql` — только минимальная модель Auth в одноразовой PostgreSQL, не облачная миграция.
- `tests/test_auth_sql.py` — реальные ограниченные LOGIN-соединения, проверки ACL/RLS/ограничений, административные контроли и конкуренция.

Локальный запуск из корня репозитория после подготовки Docker:

```sh
docker pull postgres@sha256:839fbb5a4942a7758dd93e18b42ea5649807491a0545b5eeeb8f0b8bb11857a5
python3 -m unittest discover -s supabase/tests -p test_auth_sql.py -v
```

Тест принудительно использует локальный Docker socket, одноразовый контейнер `--network none` без портов и tmpfs. Облачные DSN/пароли/ключи не требуются. При недоступном Docker тест завершается ошибкой, не обращается к облаку и не выдаёт пропуск за успех. Контейнер удаляется после прогона.

Отчёт `build/stage3b-sql-results.json` содержит только вымышленные UUID/данные, действительные SQL-роли, операции, результаты и механизм отказа. Сценарии под `postgres` — контроли/проверка транзакций, не доказательство клиентского RLS. `auth.uid()` моделируется через GUC, подпись JWT/PostgREST не моделируется.

Административные шаблоны требуют ручной замены UUID-заглушек и отдельного разрешения целевого проекта. `p_operator` не удостоверяет человека; все записи помечены соответственно. Флаг подтверждения не обходит защиту последнего администратора. Откат не предусматривает безусловное удаление таблиц или аудита.
