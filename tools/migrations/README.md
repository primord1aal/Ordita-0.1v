# Локальная проверка механизма миграции

Актуальное изменение от 9 ноября 2026 года: владелец согласовал замену исполнителя Apply на одну ограниченную PostgreSQL-транзакцию с совместимой историей CLI. Preview/Inspect продолжают читать через IPv4 Session pooler; CLI планирует только на восстановленном локальном снимке без внешней сети. Облачные команды без отдельного разрешения не запускать. Исторические [план](../../docs/STAGE_3B_MIGRATION_RUNBOOK.md) и [отчёт Preview](../../docs/STAGE_3B_PREVIEW_LOCAL_REPORT.md) описывают прежний путь Apply через CLI; текущий исполнитель описан ниже.

## Атомарный исполнитель Apply

`Database.apply_migration()` повторно проверяет единственный SQL-файл и его закреплённый SHA-256. Исходный файл, версия `202611050001`, workflow, Ref/SHA/TLS-проверки и Environment не меняются.

Один psql-процесс с `ON_ERROR_STOP=1` выполняет `BEGIN TRANSACTION READ WRITE`, ставит уникальную метку и серверные `SET LOCAL`: statement timeout 30 секунд, lock timeout 5 секунд, idle-in-transaction timeout 15 секунд. Значения проверяются на сервере **до любого DDL**, включая создание истории. Затем берётся транзакционная блокировка, повторно проверяются исходные условия, выполняется неизменённый SQL и записывается версия. Всё завершается одним COMMIT; SQL-ошибка или отказ записи истории откатывают изменения вместе.

Формат `supabase_migrations.schema_migrations` совместим с закреплённым CLI 3.0.0: `version text PRIMARY KEY`, `statements text[]`, `name text`. В `statements` сохраняется точный исходный SQL одним элементом массива. Служебные команды исполнителя в исходную миграцию и её текст в истории не добавляются. Это регистрация первой миграции, не repair существующей истории. Наличие любой версии внутри транзакции запрещает применение; конкурентные вызовы не создают вторую версию.

Облачный runner не вызывает CLI ни для dry-run, ни для применения. До записи он требует успешный Preview того же SHA/Ref/SQL и исполнителя `postgres_transaction_v1`, ровно одну ожидающую миграцию в локальном плане, пустую живую историю и прежний отпечаток. После записи выполняется прежний postflight каталога/прав. Новый SHA требует нового Preview; старый №25 от `b51a0d2` не является допуском для нового кода.

Серверные пределы относятся к отдельным SQL-операциям/ожиданиям; они не являются общим deadline всей транзакции. Окно выполнения SQL-клиента — 120 секунд; подготовка, очистка и проверка отмены имеют отдельные короткие пределы. При таймауте выполняется прежняя адресная отмена по метке, PID и времени старта backend, без воздействия на чужие сеансы. Потеря подтверждения COMMIT или ошибка postflight всё равно означает неизвестный итог: отчёт сохраняется, автоматического повтора нет, нужен отдельно согласованный Inspect. Ручное одобрение Environment и запрет любой предыдущей попытки Apply сохраняются.

Локально подтверждено, что прежние startup-параметры CLI через Supavisor дают `0/0/0`; поэтому этот путь больше не используется для облачного Apply. Клиент `Database.cli()` оставлен только для изолированных проверок совместимости. Preview выполняет CLI dry-run на локальной копии; он не исполняет SQL миграции и не подтверждает облачные права. Ограничения логического экспорта/модели Auth и хранения копии остаются прежними.

Файлы:

- `lock.json`, `install_cli.py` — CLI 3.0.0, официальный архив с проверкой SHA-256; фиксированные миграция, PostgreSQL и тестовый Supavisor 2.9.13.
- `policy.py` — чистые проверки события/ветки/SHA/Ref/URL/Environment/preview/истории попыток.
- `repository_gate.py` — предварительный job без Environment, секретов/API/БД; отдельный Repository-флаг, отсутствие дублей Environment-флага/SHA, output только `repo_enabled=true`.
- `github_gate.py` — будущая read-only проверка реальных защит GitHub; выполняется до выдачи процессу секрета БД.
- `dbtools.py`, `atomic_apply.py` — ограниченные SQL-чтения, pg_dump и один атомарный Apply с проверкой источника, серверными пределами и историей версий; пароль не попадает в URL/argv. Read-only клиенты не применяют миграцию.
- `backup.py`, `local_plan.py` — зашифрованный экспорт, расшифровка и восстановление; CLI dry-run только на проверенной локальной копии с TLS, `--network none` и подтверждённым удалением собственного контейнера. Облачного restore нет.
- `cloud_run.py` — режимы preview/apply/inspect; требует файл допуска текущего запуска GitHub. Preview №25 успешно прошёл на `b51a0d2`; новый исполнитель пока проверяется локально/CI и в облаке не запускался.
- `request_run.py` — только генератор JSON API-запроса, без отправки и облачных подключений.
- `tests/` — негативные unit-проверки и модели последовательности runner; `supabase/tests/test_migration_cli.py` — настоящие интеграционные проверки CLI и копии; `test_preview_pooler.py` — Preview через настоящий Supavisor; `test_b1_*.py` — ограничения, таймауты и очистка на PostgreSQL.

Для разработчика с локальными Python 3.12, Docker, OpenSSL и GnuPG. Загрузка инструментов обращается только к их публичным дистрибутивам; сами SQL/CLI-тесты используют контейнеры без сети и порты не публикуют. Реальные Supabase Variables/Secrets не нужны:

```sh
python3 tools/migrations/install_cli.py /tmp/orbita-cli
docker pull postgres@sha256:839fbb5a4942a7758dd93e18b42ea5649807491a0545b5eeeb8f0b8bb11857a5
docker pull supabase/supavisor@sha256:07f1a6098ffc04b80263bca4eb5c3e7bd2e03dfd1fc465aa108d7329000a1a4e
python3 -m unittest discover -s tools/migrations/tests -v
ORBITA_SUPABASE_CLI=/tmp/orbita-cli/supabase python3 -m unittest discover -s supabase/tests -p test_migration_cli.py -v
ORBITA_SUPABASE_CLI=/tmp/orbita-cli/supabase python3 -m unittest discover -s supabase/tests -p test_preview_pooler.py -v
ORBITA_SUPABASE_CLI=/tmp/orbita-cli/supabase python3 -m unittest discover -s supabase/tests -p 'test_b1_*.py' -v
python3 -m unittest discover -s supabase/tests -p test_auth_sql.py -v
```

Предыдущая подготовка Preview включала 68 unit/model-проверок, 6 CLI/backup, 8 Supavisor и 10 B1. Диагностика BACKUP добавила 7 unit-проверок. Текущий атомарный исполнитель добавляет ещё 8 unit-проверок и 7 реальных сценариев Supavisor: полный postflight/совместимость CLI, SQL-ошибку, отказ истории, серверный и клиентский таймауты, блокировку и конкуренцию. Результаты нового прогона/CI сообщаются отдельно; старые числа не являются его результатом. Отдельные 17 SQL-сценариев, Flutter и Android входят в CI. Docker-наборы локально запускаются последовательно: их контроль очистки сравнивает исходный состав контейнеров.

`build/migration-cli-results.json` и `build/preview-pooler-results.json` содержат только синтетические результаты одноразовых БД. Их допустимо хранить как артефакты. Из облачного runner никогда не публикуются raw stdout/stderr CLI, открытые дампы, manifest с содержимым проекта, пароли и секретная фраза. Разрешены только подготовленные JSON-отчёты и зашифрованный `snapshot.tar.gpg`.

Локальное повторное `db push` проверено как no-op благодаря записанной версии. Это не разрешение повтора в облаке: неизвестный результат расследуется отдельно, Re-run/любая предыдущая попытка apply блокируются. Автоматических repair/reset/повторов и пути обхода нет.
