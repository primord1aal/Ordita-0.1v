# ОРБИТА 0.5.3 — расширенная проверка API

Дата: 5 ноября 2026 года, Asia/Novosibirsk. Ветка `codex/orbita-stage-3b-auth`. Это контрольная точка доступности до серверных ролей/авторизации; облачные настройки и миграции не выполнялись.

## Переданные владельцем результаты 0.5.2

| Сеть | Запросов передано | HTTP 200 | Ошибок в переданных запросах | Время |
|---|---:|---:|---:|---|
| Wi-Fi | 1 | 1 | 0 | 739 мс |
| Мобильная, Yota по сведениям владельца | 1 | 1 | 0 | 440 мс |

Это два успешных запроса непосредственно из Android. Точное время запросов, холодные запуски и полная серия по новому протоколу не переданы. В 0.5.2 сеть выбиралась вручную; автоматического определения не было. Эти два результата сохраняются как предварительные и не объявляются завершённой расширенной приёмкой.

## Утверждённая первоначальная приёмка

- Минимум **10 последовательных запросов Wi-Fi и 10 мобильных**.
- На каждой сети минимум **два действительно разнесённых по времени окна**.
- На каждой сети хотя бы **три запроса после отдельных холодных запусков** процесса.
- Требуется **10 из 10 HTTP 200 на каждой сети**, каждый не дольше **3 секунд**.
- VPN и прокси выключены, TLS-проверка включена; используются обычные подключения будущих водителей.
- Отдельно проверяется отсутствие сети и успешный повтор после восстановления.

Неудачные или медленные результаты не удалять ради красивой серии. При нарушении условий зафиксировать причину и согласовать дополнительные испытания/решение. Не трактовать успех серии как гарантию 24/7. До подтверждения этих условий роли/авторизация не объявляются готовыми.

## Что изменено в диагностике

### Сеть Android и ручные условия

Приложение получает через `ConnectivityManager` снимки активной сети для приложения **до и после** запроса. Для этого добавлено обычное разрешение `ACCESS_NETWORK_STATE`, без запроса геопозиции или чтения SIM/номера телефона.

Выбор «Сеть для серии» — намерение владельца. Если Android определил другую сеть, запрос не отправляется. VPN/прокси, обнаруженные системным снимком, также блокируют испытание. При неизвестном типе показывается **«Не определено»**, требуется явное ручное подтверждение, и происхождение сведений остаётся видимым в отчёте.

Оператор и частный DNS задаются владельцем; приложение не выдаёт их за автоматическое измерение. Поля используют перечисления, не произвольный текст. VPN/прокси владелец подтверждает выключенными. Android-снимки и ручные сведения экспортируются раздельно.

Совпадение снимков — свидетельство устойчивой активной сети в двух моментах, не трассировка каждого пакета. Сокет специально к сети не привязывается. Каждый HTTP-запрос создаёт новый клиент без повторного использования старого соединения; обнаруженная смена сети помечается для отдельного разбора и не засчитывается автоматически. Быстрые промежуточные смены между снимками полностью исключить этим методом нельзя.

### Домен и ошибки

Показываются домен фактического адреса запроса и «Домен соответствует конфигурации» / «Домен не соответствует конфигурации». Ожидаемый домен строится из `SUPABASE_TEST_PROJECT_REF`. До отправки сверяется полный адрес health; несовпадение блокирует HTTP. Транспорт возвращает использованный адрес, который перепроверяется после ответа. Перенаправления не выполняются.

Совпадение означает внутреннюю согласованность конфигурации, а не независимое доказательство принадлежности облачного проекта. Владелец сверяет домен с Dashboard нового тестового проекта. Настоящие идентификаторы не прописываются в исходниках или workflow.

Различаются отсутствие сети, ошибка подключения, таймаут, TLS, HTTP-ошибка с кодом, перенаправление, неожиданный ответ и корректный JSON здоровья GoTrue. HTTP 200 с неожиданным содержимым не становится успехом. Таймаут HTTP — 12 секунд плюс ограниченные снимки сети, суммарно около 15 секунд. Сертификаты проверяются штатным клиентом. Причина «проект на паузе» автоматически не придумывается.

### Журнал и копирование

Запись содержит время/часовой пояс, выбранное окно, ожидаемую и наблюдаемую сеть, источник сведений, оператора, DNS, VPN/прокси, домен/сверку, HTTP-код, задержку и результат. Время для показа округляется вверх до миллисекунды; проверка порога использует реальную длительность.

Кнопки **«Скопировать результат»** и **«Скопировать текущую серию»** используют только разрешённые диагностические поля. API-ключи, пароли, токены, тело HTTP-ответа и внутренний сетевой handle не копируются. Для различения процессов создаётся случайная временная метка Android, не идентификатор устройства и не Auth-токен. Номер попытки позволяет отличать первый диагностический запрос процесса.

Журнал хранится только в памяти процесса, сохраняется при переходе между экранами, но **обнуляется после холодного запуска**. Постоянный файл не создаётся. Перед завершением процесса скопировать серию и сохранить её в своих заметках либо передать владельцу отчёта. Один буфер обмена не заменяет сбор всех предыдущих серий.

Предел — 100 записей; первые записи не удаляются молча. При заполнении новые пробы блокируются до явной очистки, перед которой предлагается копирование. Для отчёта повторно скопированные записи различаются по метке процесса и номеру попытки; дубликаты не считаются новыми запросами.

Все четыре Variables уже добавлены владельцем; их значения в инструкции не повторяются. Новый workflow сохраняет защиту точного HTTPS-домена/разрешённого и запрещённого Project Ref и не передаёт эти значения изолированным тестам.

Открыть [Actions ветки](https://github.com/primord1aal/Ordita-0.1v/actions?query=branch%3Acodex%2Forbita-stage-3b-auth), выбрать успешный запуск текущей версии и скачать **ORBITA-0.5.3-api-check-apk**. В ZIP — `ORBITA-0.5.3-api-check.apk`, `SHA256SUMS.txt`, эта инструкция под именем `INSTALL-ANDROID.md` и документ `SUPABASE_FREE_RELIABILITY.md`. Артефакт хранится 14 дней. Нужен вход в GitHub; Flutter на компьютере владельцу не требуется.

Это ARM64 debug APK для Tecno, minSdk 24. При несовместимой тестовой подписи замена старой тестовой установки проводится отдельно; она сбросит её локальные данные/разрешения. Исходники/публикация принятой 0.5.1 сохраняются. Длительные GPS-прогоны остаются отдельными.

## План испытаний владельца — выполнять по одному действию

Перед каждым блоком проверить обычное подключение, VPN/прокси, DNS. В приложении: режим просмотра → Профиль → Проверка API. Выбрать сеть, для мобильной указать оператора, выбрать DNS и окно, подтвердить условия. Проверить показанный домен. В журнале учитывать Android-снимки, а не только выбранную кнопку.

Предлагаемая раскладка:

| Сеть | Окно 1 | Окно 2 позже | Холодные запуски |
|---|---|---|---|
| Wi-Fi | 5 запросов, среди них первые запросы двух отдельных процессов | 5 запросов, первый — после третьего холодного запуска | Минимум 3 |
| Мобильная | 5 запросов, среди них первые запросы двух отдельных процессов | 5 запросов, первый — после третьего холодного запуска | Минимум 3 |

Пример для пяти запросов первого окна одной сети: после холодного запуска сделать два запроса, скопировать/сохранить серию; полностью остановить приложение, открыть заново и сделать ещё три. Второе окно — реально позже, желательно в другое время дня; смена метки «Окно 1» на «Окно 2» сама по себе разнесение не доказывает. Новый минимальный временной интервал здесь не вводится.

Для холодного запуска использовать полноценную остановку приложения через системные сведения о нём и затем открыть заново. Переключение вкладок, уход на главный экран и простое смахивание списка приложений не гарантируют прекращения процесса. До остановки сохранить копию предыдущего журнала. Первая проба в новом процессе получает новую метку и номер попытки 1. Точные названия меню HiOS зависят от сборки и здесь не выдумываются.

### Отсутствие сети — отдельный сценарий

Выбрать **«Без сети / восстановление»**, чтобы ожидаемая ошибка не смешивалась с приёмочными окнами. Открыть диагностику, включить режим самолёта и убедиться, что Wi-Fi тоже выключен: Android может сохранять Wi-Fi в этом режиме. Нажать «Проверить связь».

Ожидается понятная ошибка без зависания/аварии. Если Android достоверно сообщает отсутствие сети, HTTP не отправляется и ошибка появляется сразу. При нераспознанной проблеме действует ограниченный таймаут. Затем восстановить обычное подключение и повторить: ожидается нормальный ответ, без переустановки и перезапуска ради восстановления. Скопировать обе записи отдельно от 10+10 успешной серии.

Это пока план физического испытания. Модельные тесты проверяют обработку состояния/повтор, но не являются результатом режима самолёта на Tecno.

## Проверки кода

Локально прошли **122 Flutter-теста**, отдельная CLI-проверка разрешённой/запрещённой конфигурации, **19 Android-тестов** без пропусков (включая модель сети на API 24 и 34), анализ Dart, Android Lint без ошибок и сборка неподключённого ARM64 APK 0.5.3. Модели проверяют также потерю сети, повтор после восстановления, таймаут/TLS/HTTP, копирование разрешённых полей и крупный системный шрифт. Эти результаты не заменяют реальный телефон. Изоляция тестов в Linux network namespace и подключённая сборка подтверждаются отдельным успешным запуском GitHub Actions, а не наличием workflow.

## Что передать и что остаётся непроверенным

Передать скопированные блоки с условиями и временами. Указать версию 0.5.3. Анализ отдельно посчитает уникальные запросы по каждой сети, HTTP-ошибки/таймауты, превышения 3000 мс, окна и разные процессы. Серверные логины, роли, RLS, SQL и Refresh Token этим тестом не проверяются.

Сейчас переданы только две предварительные успешные пробы 0.5.2. Расширенная серия, холодные прогоны и отсутствие сети на физическом устройстве не приняты. При провале не делать вывод о паузе Supabase без подтверждения Dashboard; исследовать наблюдаемую ошибку и отдельно согласовать решение.

## Supabase Free и следующий шаг

[Проверенные условия паузы и риски коммерческой эксплуатации](SUPABASE_FREE_RELIABILITY.md): возможна пауза при низкой активности за семь дней, есть письма владельцу и возобновление через Dashboard; текущая официальная страница указывает окно восстановления до года. Единого HTTP-кода паузы не заявлено. Тариф/инфраструктура не менялись.

Только после подтверждения расширенной доступности — подготовка `orbita_profiles`, отдельной `orbita_user_roles`, миграций, RLS/привилегий и защищённых административных операций, отрицательных локальных тестов и архитектуры Flutter Auth с явным secure storage. До применения облачных миграций показать точный целевой Project Ref, операции/объекты, локальные результаты, риски и план проверки и остановиться для отдельного разрешения. Роль только из актуальной серверной таблицы; `PUBLIC`/`anon`/`authenticated` не получают EXECUTE административных функций. Карты, заказы и Push не начинаются автоматически.
