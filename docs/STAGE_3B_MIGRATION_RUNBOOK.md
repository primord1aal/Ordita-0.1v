## 1. Как запустить workflow без изменения main

В `main` отдельным ранее разрешённым действием добавлен файл `.github/workflows/orbita-stage-3b.yml`. Вспомогательных `tools/migrations/`, приложения и миграций там нет. В **Run workflow → Use workflow from** обязательно выбирать `codex/orbita-stage-3b-auth`. Поле `approved_sha` не выбирает исходную ветку. Запуск №18 из `main` остановился на отсутствующем `install_cli.py` до облачных шагов; Inspect №19 из рабочей ветки прошёл.

У GitHub есть отдельный документированный случай: **если workflow уже запускался, его можно вызвать через API или GitHub CLI с указанием ветки/тега**. Наш существующий workflow уже зарегистрирован. Read-only проверка GitHub вернула ID **407235349**, состояние `active` и нужный путь. Исторический успешный запуск — [№42069441284](https://github.com/primord1aal/Ordita-0.1v/actions/runs/42069441284).

Для автоматизированного ручного запуска используем **существующий workflow 407235349 через GitHub API**, передав `ref: codex/orbita-stage-3b-auth`. GitHub выполнит файл из указанной ветки. Второй workflow, изменение `main` или переключение default branch не требуются. Каждый новый облачный запуск отдельно согласуется; ошибка API или задания не разрешает автоматический повтор.

Разработчик может подготовить JSON локальным `tools/migrations/request_run.py`. Он **не отправляет запрос**. Будущий запуск выполняется одним явно разрешённым POST к `/repos/primord1aal/Ordita-0.1v/actions/workflows/407235349/dispatches` с этим JSON. Поле API `ref` — ветка; согласованный полный SHA передаётся отдельным input и проверяется до подключения к БД. Если ветка успела переместиться, запуск отклоняется.

## 2. Что изменено в workflow

| Режим | Способ запуска | Обращение к облачной БД | Результат |
|---|---|---|---|
| `verify` | Обычный push в рабочую ветку либо ручной API | Нет | Локальные SQL/CLI/Flutter/Android-проверки и тестовый APK |
| `preview` | Отдельный ручной API и подтверждение Environment | Только чтение и логический экспорт; dry-run выполняется на восстановленной локальной копии без внешней сети | Предварительный отчёт и зашифрованный снимок |
| `apply` | Новый ручной API и новое подтверждение Environment | Одно применение через CLI, затем чтение | История версии и проверка каталога/прав |
| `inspect` | Отдельный ручной API и подтверждение Environment | Только чтение состояния | Наблюдение после ошибки; применения нет |

Ключевые условия подготовленного YAML:

```yaml
# Дополнительно защищённый job требует успешный migration_entry и точную ветку.
if: github.event_name == 'workflow_dispatch' && inputs.migration_operation == 'apply' && vars.ORBITA_REPO_MIGRATIONS_ENABLED == 'true' && needs.migration_entry.outputs.repo_enabled == 'true' && github.ref == 'refs/heads/codex/orbita-stage-3b-auth'
environment: orbita-mobile-test-migrations
```

`push` не может выполнить облачные job: их условие требует другого события. Пустой переключатель допуска тоже запрещает запуск. Проверки этого условия входят в локальные тесты. Простой push не выдаёт секреты БД. `verify` не использует Environment с секретами миграции.

Облачные запуски имеют общую группу `orbita-cloud-migration-single-flight` с `cancel-in-progress: false`. Обычная сборка использует другую группу и не отменяет применение. Не запускаем несколько облачных операций одновременно и не отменяем активное применение вручную без необходимости: отмена не доказывает откат.

### Обязательные настройки GitHub — этой подготовкой не менялись

Environment — защищённый раздел GitHub, который задерживает job до ручного допуска и только затем открывает его секреты. Для публичного репозитория необходимые защиты доступны на GitHub Free.

| Где | Имя | Требование |
|---|---|---|
| Environment | `orbita-mobile-test-migrations` | Required reviewer — владелец `primord1aal`; требуется фактическое ручное одобрение каждого облачного запуска |
| Его deployment branches | Selected branches and tags | Единственная точная ветка `codex/orbita-stage-3b-auth`, тип branch; без `*`, других веток и тегов |
| Repository Variable | `ORBITA_REPO_MIGRATIONS_ENABLED` | Предварительный допуск, при отсутствии/`false` запуск запрещён. Владелец ранее включил его для контролируемых запусков; эта подготовка его не меняет и не трактует как разрешение нового подключения |
| Environment Variable | `ORBITA_CLOUD_MIGRATIONS_ENABLED` | Окончательный допуск внутри job после ручного подтверждения. Владелец показал установленное `true` перед Inspect №19; этой работой не переключается |
| Environment Variable | `ORBITA_ALLOWED_MIGRATION_SHA` | Полный SHA отдельно проверенного и опубликованного коммита. Владелец сообщил добавление этой переменной; для исправленного коммита SHA пересогласуется отдельно |
| Уже существующие Repository Variables | `SUPABASE_TEST_PROJECT_REF`, `SUPABASE_FORBIDDEN_PROJECT_REF` | Точный разрешённый и запрещённый Ref; значения не менялись |
| Environment Variable | `ORBITA_TEST_DB_URL` | Строка PostgreSQL **без пароля**, порт 5432, база postgres, `sslmode=verify-full` |
| Environment Variable | `ORBITA_TEST_DB_CA_PEM` | Публичный CA/набор CA, подходящий выбранному endpoint; получать по официальным данным проекта/подключения |
| Environment Secret | `ORBITA_TEST_DB_PASSWORD` | Пароль БД, введённый владельцем непосредственно в защищённый GitHub; не Repository Secret |
| Environment Secret | `ORBITA_BACKUP_PASSPHRASE` | Отдельная случайная длинная фраза для шифрования копии; минимум 24 символа; вторая сохранённая копия — у владельца вне GitHub |

Названия настроек выше относятся к GitHub, не к меню телефона. Пользовательские пароли, `service_role`, `sb_secret` и Supabase Management API token этому механизму не нужны. Эти настройки сейчас не запрашиваются и не меняются.

Не копировать Environment-флаг/SHA на уровень repository/organization. Новый job `migration_entry` без Environment проверяет отдельный Repository-флаг и отсутствие этих двух имён вне Environment; при дубликатах, даже со значением `false`, отказывает до ручного допуска. Только его output `repo_enabled=true` позволяет защищённым job продолжить. Environment-флаг/SHA читаются затем через `steps.env` внутри job. При `false`/пустом значении gate завершается отказом до API и БД. Это устраняет зависимость `jobs.if` от ещё недоступных Environment Variables; [документация и локальные тесты](STAGE_3B_VARIABLE_SCOPE_FIX.md).

Для GitHub-hosted runner сохраняем **Session pooler, порт 5432**, по строке из Dashboard: он подходит для IPv4. Адрес не угадываем, пароль из строки удаляем до сохранения Variable. TLS проверяет именно имя выбранного endpoint и его доверенную цепочку; сертификат прямого DB-host нельзя заранее считать подходящим pooler. Inspect №19 подтвердил соединение и чтение через этот endpoint с `verify-full`. Экспорт и полная цепочка нового Preview в облаке ещё не проверены. Ошибка TLS — остановка без переключения на `sslmode=require`/отключения проверки.

Одного названия `environment:` в YAML недостаточно: GitHub может создать пустое Environment без защиты. Поэтому перед выдачей пароля отдельный шаг читает **реальные** правила, разрешённые ветки и историю одобрений текущего запуска через GitHub API. Нет правил, одобрил другой человек, API недоступен, использован обход допуска — подключение к БД запрещено. Для одного владельца допускается подтверждение собственного запуска; это ручное подтверждение, не правило двух разных людей.

Владелец репозитория технически способен изменить workflow/защиты или удалить историю запусков. Это граница модели доверия. Такие административные изменения не считаются разрешённым способом повтора.

## 3. Версия CLI, транзакция и история

Закреплён **Supabase CLI 3.0.0**, официальный Linux AMD64 архив. SHA-256 архива:

```text
eeb61edcd59a4735fcb5e58596574f25d03d420efca779f43ddb307e1cc5c754
```

Установщик проверяет сумму до запуска. PostgreSQL 17 закреплена digest образа. Версии, имена и суммы записаны в [lock.json](../tools/migrations/lock.json).

Разрешён единственный файл `202611050001_stage3b_auth.sql`, версия **`202611050001`**. Его новый SHA-256:

```text
31bf9839b8574680ace8cb168317a158b41e94a31a789f192033720afb36d79b
```

Из прежнего файла удалены **только два внешних оператора** `begin;` и `commit;`. Внутренние PL/pgSQL `BEGIN/END`, таблицы, функции, политики и триггеры сохранены. Внешнюю транзакцию теперь задаёт закреплённый CLI. Для этого файла он выполняет DDL и запись версии в `supabase_migrations.schema_migrations` в одной транзакции. Тест с искусственным отказом вставки истории подтвердил откат уже выполненного DDL.

Сам SQL-файл не следует вставлять в SQL Editor: он больше не содержит внешней транзакции и такой запуск не зарегистрирует историю CLI. Административные шаблоны `supabase/admin/` — отдельные будущие операции, они этой процедурой не выполняются.

12-значная версия допустима для проверенного CLI. Сохраняем её, не переименовываем. `migration list` сравнивает версии, а не контрольные суммы файлов; поэтому SHA файла и коммита проверяются независимо.

При первом применении CLI может предварительно создать пустую служебную таблицу истории. При ошибке это служебное основание может остаться, но **версия и прикладные объекты откатываются вместе**. Это не признак применённой миграции.

При любом отклонении следующий шаг не выполняется. Успешное применение не разрешает создавать пользователей, менять Auth или переходить к следующей части проекта.

### Что действительно проверяет preview

Перед подключением проверяются: событие, repository, точная ветка, попытка №1, **равенство SHA запроса, запуска, checkout и разрешающей Variable**, один файл и его SHA. Адрес соединения должен быть либо `db.<разрешённый-ref>.supabase.co` с пользователем `postgres`, либо Session pooler Supabase с пользователем `postgres.<разрешённый-ref>`. Порт — только 5432, TLS — `verify-full`. Пароль в URL, порт 6543, старый/другой Ref, дополнительные параметры соединения запрещены.

Облачная часть выполняет фиксированные запросы в явной транзакции `BEGIN TRANSACTION READ ONLY` с `SET LOCAL` для идентификатора операции и серверных таймаутов. Параметры запуска `PGOPTIONS` не считаются доказательством этих ограничений через pooler. `pg_dump` самостоятельно открывает READ ONLY-транзакцию; сохраняются ограничение ожидания блокировки и клиентский срок выполнения с остановкой собственного процесса/контейнера.

**Облачный CLI в Preview запрещён**, даже с `--dry-run`. После экспорта, шифрования, обратной расшифровки и восстановления проверенный CLI запускается только внутри собственного контейнера PostgreSQL с `--network none`. В него не передаются пароль, URL и API-токены облака. Проверяются точный CID/метка владельца, отсутствие сети, локальный TLS и SHA единственного файла миграции. Цель CLI фиксирована:

```text
supabase db push --remote=postgresql://postgres@localhost:5432/restore?sslmode=verify-full&sslrootcert=/tmp/orbita-restore-ca.pem --skip-vault --dry-run
```

Это описание аргументов локального процесса, не команда для выполнения владельцем. История восстановленной копии должна совпасть с прочитанной облачной историей; после CLI проверяется неизменность истории и согласованного состояния копии. CLI не использует `link`, сохранённый облачный DSN, Management API, seed, custom roles или Vault. В отчёте явно записывается `cli_dry_run_target=isolated_restored_snapshot`.

Dry-run должен сообщить **ровно одну ожидающую миграцию** — `202611050001_stage3b_auth.sql`. Ноль, две, неизвестный формат или дополнительные операции — отказ. **Dry-run не исполняет весь SQL и не доказывает успешность его операций, наличие всех прав, получение блокировок или работу RLS в облаке.** Эти риски снижают локальное реальное применение и проверки после облачного применения; они остаются разными доказательствами.

Preview формирует отпечаток публичных объектов, функций, части метаданных/прав, количества строк и Auth-триггеров. После экспорта и локального планирования облачное состояние и отпечаток читаются повторно; при отличии успешного отчёта нет. Перед apply они проверяются снова. Это дополнительный контроль изменений в согласованном объёме, **не полный снимок состояния проекта**. Поэтому отсутствие параллельных изменений — обязательное условие работы.

**До Apply остаётся отдельный вопрос:** серверные таймауты облачного CLI через Session pooler ещё не подтверждены. Локальное выполнение Preview устраняет этот риск для предварительной проверки, но не доказывает готовность пути применения. При обрыве клиента нельзя обещать мгновенную остановку серверного процесса. Успешный Preview не разрешает Apply и не снимает необходимость решить этот вопрос.

### Почему случайный повтор остановится

Apply требует успешный preview **того же SHA/ветки/Ref/файла** и действительные артефакты. Перед выдачей пароля gate скачивает их, проверяет состав ZIP и хеш зашифрованного файла. После соединения заново проверяет пустую историю/исходные объекты и dry-run.

Кнопка GitHub **Re-run jobs** запрещена политикой `run_attempt == 1`. Кроме того, любая более ранняя ручная попытка `apply` этого workflow блокирует новый apply — даже `failed` или `cancelled`, в том числе отказ до записи. Это намеренно консервативный механизм первой миграции. После выяснения причины нужен новый отдельно согласованный план; готовой кнопки обхода нет. Историю запусков не удаляем ради обхода.

## 5. Проверяемая копия и пределы восстановления

На Free нет автоматической резервной копии по подтверждению владельца. Перед первой миграцией делаем **зашифрованный логический экспорт согласованной части базы**, а не обещаем полную копию Supabase.

1. Условие этой процедуры — 0 Auth-пользователей, отсутствие новых прикладных объектов и данных в публичных таблицах. Найдены пользователи/данные — остановка и отдельный план.
2. `pg_dump --format=custom` сохраняет `public` и, если существует, `supabase_migrations`. Отдельный manifest сохраняет перечень таблиц/число строк, имена SQL-ролей без паролей и определения пользовательских триггеров `auth.users`.
3. Архив `before.dump` + `manifest.json` шифруется GPG AES-256. Проверяется обратная расшифровка и совпадение SHA исходного/расшифрованного архива. Неправильная фраза должна приводить к ошибке.
4. Дамп извлекается именно из проверенного расшифрованного архива и восстанавливается в **новую одноразовую локальную PostgreSQL без сети** с локальным TLS. Минимальная модель Auth даёт зависимости для DDL. Проверяются восстановление, состав публичных таблиц и число строк; затем CLI проверяет план на этой копии. Контейнер принадлежит операции по точному CID/метке; удаление подтверждается через Docker. Неизвестный результат или неподтверждённое удаление не дают успешного отчёта.
5. В Actions попадают только `snapshot.tar.gpg` и отчёт без содержимого таблиц/секретов. Открытые файлы остаются во временной папке runner и удаляются при нормальном завершении. При принудительном обрыве не обещаем гарантированное затирание диска; используется одноразовый GitHub-hosted runner, не постоянная машина.
6. Владелец скачивает зашифрованный файл до apply и сохраняет отдельно от фразы. Артефакты GitHub живут **14 дней** и не заменяют независимое хранение. Потеря фразы делает этот файл невосстановимым.

**Что эта проверка не восстанавливает и не доказывает:** управляемые схемы/данные Auth и Storage, файловые объекты Storage, пароли/членство SQL-ролей, настройки Auth/проекта/сети, серверные расширения/инфраструктуру, восстановление на момент времени. Имена ролей в manifest — не резервная копия их полномочий. В локальном restore применяются `--no-owner --no-privileges`: он проверяет DDL/таблицы/строки, **не сохранность владельцев и ACL**, не настоящий Supabase Auth и не полное восстановление проекта. Определения Auth-триггеров в manifest не означают их автоматическое восстановление в облаке.

Для первой миграции пустого тестового проекта это проверяемая дополнительная страховка с явно ограниченным объёмом. До настоящих пользователей/поездок нужен отдельный полный план резервирования и подтверждённое восстановление нужного объёма Supabase.

**Если действительно потребуется восстановление:** останавливаем запись и сохраняем отчёты/аудит/текущее состояние; расшифровываем сохранённую копию в закрытом окружении, повторяем локальный restore. Затем отдельно проектируем восстановление на новом тестовом проекте Supabase с совместимой версией, расширениями, владельцами, ACL и настройками. Только после проверки зависимостей и нового разрешения выполняем выбранное восстановление. Восстановления поверх текущей облачной БД в этом workflow нет. При уже совершённом COMMIT обычный путь исправления — новая версионная миграция после разбора причины.

## 6. Действия при ошибке

| Наблюдение | Что оно означает | Разрешённый следующий путь |
|---|---|---|
| Не прошёл gate/preview | Применение не начиналось | Сохранить ошибку; разобрать настройку/Ref/SHA. Не нажимать Re-run; новый preview — после согласования |
| Dry-run показывает не одну версию | План отличается от ожидаемого | Остановиться; обследовать историю и файлы. Не использовать `migration repair` |
| SQL-ошибка, история и объекты отсутствуют | Совместимо с откатом; возможна пустая служебная история | Сохранить отчёт; отдельно исправить причину и согласовать следующий план. Автоматического повтора нет |
| CLI завершился/связь оборвалась, postflight не получен | COMMIT мог произойти | Считать исход неизвестным. Не запускать apply повторно. Отдельно разрешить `inspect` |
| Версия есть и структура/права совпали | Миграция применена | Сохранить результат; не применять снова, даже если предыдущий job красный |
| Версия есть, но структура/права отличаются; либо объекты есть без версии | Нужен разбор неполного/постороннего состояния | Не править историю автоматически. Сохранить факты; подготовить отдельно проверенную корректирующую миграцию/план восстановления |
| Нет отчёта после отмены/таймаута | Это не доказательство отсутствия COMMIT | Тот же путь расследования через `inspect`, без повторной записи |

`inspect` читает только число пользователей, наличие согласованных объектов и список версий. Он не запускает CLI и не выдаёт разрешение на повтор. Для полного разбора ACL/DDL может понадобиться отдельно согласованный расширенный read-only запрос.

В коде отсутствуют автоматические `migration repair`, `db reset`, восстановление в облако и циклы повторного применения. Пароль не включается в argv/URL, shell tracing не используется, сырые stdout/stderr БД/CLI не печатаются и не загружаются в артефакты. При отказе публикуется только разрешённый отчёт. Отладку с `--debug`, печать Environment или полных ответов добавлять нельзя.
