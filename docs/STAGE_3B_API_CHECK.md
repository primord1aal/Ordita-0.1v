# ОРБИТА 0.5.2 — проверка HTTPS API из Android

Дата: 5 ноября 2026 года, Asia/Novosibirsk. Ветка: `codex/orbita-stage-3b-auth`, основа — принятая 0.5.1 (`60383f7`). Это промежуточная контрольная точка этапа 3Б. Настоящая авторизация и весь этап пока не готовы.

## Что подтверждено владельцем

- Создан независимый `orbita-mobile-test`, статус Healthy. Владелец отдельно подтвердил его Project Ref и идентификатор старого `orbita-dev` для запрета CI.
- На Tecno KL7 / Android 14 / HiOS частный DNS — «Автоматически».
- Через Wi-Fi и мобильную Yota по адресу `/auth/v1/health` получен JSON `No API key found in request`. Условия проверки — без VPN и прокси. HTTP-код и время браузером не зафиксированы.
- Это доступность HTTPS-шлюза. Ответ самой службы Auth, стабильность и вход из Android ещё не подтверждены.
- Интерфейс 0.5.1 принят на настоящем телефоне, включая максимальный шрифт. Длительные GPS-прогоны 10/30/60 минут остаются отдельной задачей.

## Зачем эта промежуточная сборка

В профиле добавлена «Проверка API». Только после выбора сети и нажатия кнопки она делает **GET `/auth/v1/health`** с публичным клиентским ключом тестового проекта. Аккаунт и пароль не используются. Запрос не создаёт аккаунты, таблицы или заказы и не меняет настройки облака.

Успех — HTTP 200 с ожидаемым JSON здоровья GoTrue. HTTP 401/403 не выдаётся за успешный ответ службы входа. Ошибки TLS, сети, таймаут 15 секунд, перенаправление, слишком большой/неожиданный ответ и ограничение частоты показываются отдельно. Перенаправления не выполняются; проверка сертификата не отключается.

Показываются выбранная вручную сеть, результат, HTTP-код, длительность и время. До шести последних результатов живут только на открытом экране. Метка сети сама не переключает Wi-Fi/мобильные данные. VPN, оператор и DNS автоматически не определяются.

Это ещё не проверка пароля, роли, профиля, RLS, обновления сессии или долгой фоновой работы. До результата Android-проверки не выдавать серверную авторизацию за испытанную.

## Конфигурация сборки

В GitHub открыть репозиторий → Settings → Secrets and variables → Actions → **Variables**, затем Repository variables. Используются именно Variables. Владелец заполняет их вручную, последовательно по инструкциям разработчика.

| Переменная | Значение |
|---|---|
| `SUPABASE_TEST_PROJECT_REF` | Подтверждённый владельцем идентификатор нового `orbita-mobile-test` |
| `SUPABASE_FORBIDDEN_PROJECT_REF` | Подтверждённый владельцем идентификатор существующего `orbita-dev` |
| `SUPABASE_TEST_URL` | `https://<идентификатор нового тестового проекта>.supabase.co` |
| `SUPABASE_TEST_PUBLISHABLE_KEY` | Только Publishable key нового тестового проекта, взятый в его Dashboard |

Точные идентификаторы и значения ключей не вписываются в исходники или workflow. Publishable key публичен и извлекается из APK; он не заменяет RLS и SQL-привилегии. Пароли, `service_role`, `sb_secret` и административные токены сюда не подходят и в чат не передаются.

Перед подключённой сборкой CLI проверяет все четыре значения: точный HTTPS-домен из положительного списка, совпадение разрешённого Project Ref, отличие от запрещённого, отсутствие лишних путей/портов/параметров и подходящий формат публичного ключа. Без параметров или при несовпадении сборка останавливается. При ошибке удаляется прежний временный JSON, чтобы он не мог быть использован повторно.

В APK входят только три клиентских параметра; запрещённый Project Ref остаётся параметром проверки CI. JSON конфигурации не публикуется как артефакт и удаляется в завершающем шаге. Правильную принадлежность непрозрачного publishable-ключа проекту подтверждает ответ API на телефоне; локальная проверка формата этого не доказывает.

У имеющегося у Codex GitHub-доступа чтение списка Variables вернуло HTTP 403. Это ограничение доступа GitHub, а не ошибка Supabase. Обход или изменение Variables не выполнялись.

## Изоляция CI

Отдельный workflow: `.github/workflows/orbita-stage-3b.yml`. Старый workflow и принятая ветка 0.5.1 сохраняются.

SDK и зависимости скачиваются до тестов. Затем Flutter-тесты и настоящая CLI-проверка конфигурации запускаются в отдельном Linux network namespace: наружных сетевых интерфейсов и маршрутов нет, включён только loopback. Модели сервиса используют искусственный транспорт, низкоуровневые HTTP-тесты — собственный сервер на `127.0.0.1` со случайным портом. Ни одного обращения к облачным Supabase в этих тестах нет. Значения четырёх проектных Variables им не передаются.

Компиляция без конфигурации проверяет исходники, этот APK не выдаётся владельцу как подключённый. Существующие Android-тесты и Lint проверяют нативную службу и разрешения, без Supabase SDK и конфигурации; Gradle может скачивать зависимости инструментов. После всех проверок отдельный шаг получает проектные Variables, выполняет защиту и собирает подключённый APK. В процессе сборки приложение не запускается и не обращается к API.

Нет SQL-миграций в workflow, интеграционных облачных тестов, пользовательских паролей или административных секретов. Нет автоматического выбора проекта Supabase CLI/MCP.

Локальная команда `flutter test --no-pub` тоже использует только искусственные данные/loopback. Доказательство Linux-изоляции CI — успешный конкретный запуск Actions, его нельзя вывести только из локальных тестов.

## Получение APK после заполнения Variables

Локально прошли **100 Flutter-тестов**, реальная CLI-проверка защиты сборки, **7 Android-тестов** без пропусков, анализ Dart, Android Lint без ошибок, Actionlint и компиляция неподключённого ARM64 APK 0.5.2. В новых проверках нет обращения к облачным проектам. Изоляция Linux namespace в GitHub подтверждается отдельно конкретным запуском; сам подключённый APK до Variables не собран.

Нативные 21 Android-файл основы и семь файлов старого веб-прототипа сохранены без изменений. Изменены 20 файлов: новый workflow, три корневых документа, README/версия мобильного проекта, маршрутизация и ссылка в профиле, конфигурация/HTTP-проверка/экран API, четыре файла тестов, три инструмента CI и эта инструкция. Действующий Supabase не изменялся.

1. Открыть [Actions ветки 3Б](https://github.com/primord1aal/Ordita-0.1v/actions?query=branch%3Acodex%2Forbita-stage-3b-auth), выбрать workflow «Орбита 3Б — изолированные проверки и API APK».
2. Если прошлый запуск остановлен проверкой параметров, после заполнения Variables перезапустить его. Недостающие параметры не обходить фиктивными значениями.
3. Дождаться зелёного результата. Скачать Artifacts → **ORBITA-0.5.2-api-check-apk**, распаковать ZIP.
4. Установить **ORBITA-0.5.2-api-check.apk** на Tecno. Это ARM64 debug APK, minSdk 24, не коммерческий релиз. Артефакт хранится 14 дней.
5. При несовместимой debug-подписи удалить прежнюю тестовую «Орбиту» и установить заново. Это сбросит её локальные данные/разрешения. Исходники и опубликованная принятая сборка 0.5.1 сохраняются.

Ссылку на реально завершённый запуск разработчик даёт отдельно. До готовности Variables и зелёной подключённой сборки рабочая ссылка на новый APK не заявляется.

## Проверка на Tecno — выполнять по одному шагу

После установки открыть любой режим просмотра → Профиль → Проверка API. Отдельно проверить Wi-Fi и Yota с выключенными VPN/прокси и записанной настройкой DNS. В самом экране отметить используемую сеть и нажать «Проверить связь». Для ограниченного испытания стабильности повторить три раза на каждой сети, последовательно, не параллельно.

Передать результат: тип сети, оператор для мобильной, DNS, HTTP-код, сообщения, примерные длительности. Скриншот не должен содержать посторонние личные уведомления. Отдельно проверить максимальный шрифт и сохранность локального уведомления / GPS-диагностики. Публичный ключ, пароли и токены на экране не показываются.

При ошибке сертификата, недоступности или нестабильности остановиться. Не включать VPN ради зачёта и не отключать TLS-проверку. Затем сравнить варианты размещения, региона, собственного прокси-домена или провайдера по стоимости/безопасности/обслуживанию; инфраструктуру менять только после отдельного решения владельца.

## Следующие части этапа 3Б

После подтверждённой Android-доступности продолжить авторизацию: подготовить `orbita_profiles` без привилегированной роли и отдельную `orbita_user_roles`, RLS и SQL-привилегии, отрицательные тесты на изолированной искусственной PostgreSQL, настройки Auth и явный адаптер защищённого хранилища SDK.

Перед облачной миграцией показать объекты и точный целевой проект и получить отдельное разрешение. Владелец проверяет настройки Dashboard и создаёт четыре искусственных аккаунта административным способом. При отсутствии доступа Codex выдаёт проверяемые инструкции, не объявляет настройки выполненными.

Проверяем актуальную роль только в серверной таблице, запрещаем её клиентское изменение и EXECUTE административных функций, обрабатываем отзыв роли, холодный запуск без сети и перепроверку после фона. Администратор получает нейтральный экран веб-панели. Серверные роли, Auth и эти проверки в 0.5.2 ещё не реализованы.

Карты OSM + Geoapify Free утверждены для 3В, но в эту сборку не входят. Настоящие заказы, очередь, диспетчер, GPS-передача, серверный Push, SMS, платежи и публикация RuStore не начинаются.
