# ОРБИТА 3Б — разделение Repository и Environment Variables

**6 ноября 2026 года, Asia/Novosibirsk. Только локальное исправление.** Основа — опубликованный коммит `59b89d3901090e9d97d3df4d95b21ef001a84ec0`. Новая подготовка не опубликована, Actions/облачные режимы не запускались. Настройки GitHub и Supabase этой работой не менялись.

## Что подтвердилось по документации

Для текущего размещения переменных проблема подтверждена:

- [GitHub: Configuration variable precedence](https://docs.github.com/en/actions/reference/workflows-and-actions/variables#configuration-variable-precedence): **“Environment-level variables are only available on the runner after the job starts executing.”**
- [GitHub: vars context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#vars-context): **“Configuration variables at the environment level are automatically available after their environment is declared by the runner.”** Неопределённая переменная в `vars` даёт пустую строку.
- [GitHub: jobs environment](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idenvironment): правила защиты Environment должны пройти до отправки задания runner.

`jobs.if` решает, допускать ли задание до этой стадии. Поэтому на нём нельзя ожидать доступности переменной, заданной только в Environment. В исходном плане флаг и SHA были описаны как Repository Variables. Когда они размещены в Environment, прежнее условие не получает флаг: даже последующее `true` в Environment само по себе не запустит защищённое задание. Прежний успешный push-CI проверял `verify`, а не этот путь ручного запуска.

Это вывод из официальной документации и локальной модели. Фактический защищённый запуск GitHub не выполнялся; переменные/защиты владельца через API проекта этой подготовкой не обследовались.

## Предлагаемая схема

| Уровень | Переменная | Назначение |
|---|---|---|
| **Repository** | `ORBITA_REPO_MIGRATIONS_ENABLED` — новое имя | Предварительно разрешает ручным облачным режимам пройти к проверке репозитория. Отсутствие/`false` запрещает переход. Это не разрешение на SQL |
| **Environment** `orbita-mobile-test-migrations` | `ORBITA_CLOUD_MIGRATIONS_ENABLED` | Окончательный флаг внутри защищённого задания. Существующее `false` сохраняет запрет |
| **То же Environment** | `ORBITA_ALLOWED_MIGRATION_SHA` | Полный SHA отдельно согласованного опубликованного исходного кода; проверяется внутри задания |

Указанные владельцем две Environment Variables сохраняют свои имена и уровень. Новый флаг репозитория — отдельное имя; одноимённые копии Environment-флага и SHA на уровне repository/organization запрещены. В личном репозитории организации нет; предварительный job в любом случае проверяет унаследованный контекст без Environment.

Последовательность:

1. Обычный push выполняет только изолированные проверки и тестовую сборку. Ни один из трёх job допуска к облаку при push не выполняется.
2. Только `workflow_dispatch` с режимом preview/apply/inspect, разрешённой рабочей веткой и предварительным положительным сравнением Repository-флага может начать `migration_entry`. Он **не объявляет Environment**, не использует секреты, API GitHub или БД. Внутри требует именно строку `true`, проверяет точный SHA входа/запуска/checkout, чистоту checkout, попытку №1 и отсутствие двух Environment-имён во внешнем контексте. Сравнения строк GitHub не учитывают регистр; Python-проверка намеренно строже и не выдаёт допуск при `True`/`TRUE`.
3. Только успешная проверка выдаёт output `repo_enabled=true`. Защищённые job зависят от неё и прежних SQL/CLI-проверок. Ошибка/отсутствующий output — остановка до допуска Environment.
4. GitHub отдельно запрашивает ручное одобрение защищённого Environment. Существующие ограничения ветки и обязательного reviewer сохраняются.
5. **На уровне `steps.env` внутри этого job**, после допуска, читаются Environment-флаг и SHA. `github_gate.py` требует оба независимых допуска, точный SHA и Ref, затем проверяет реальные защиты и ручное одобрение через прежние read-only API. `false`, пустое значение, другой SHA — ошибка до этих API и до подключения к БД.
6. Только успешный gate допускает прежний шаг с Environment Secret пароля БД. Preview/apply/inspect остаются разными режимами, автоматических повторов/repair/reset нет.

Оба допуска нужны одновременно. Например, Repository=`true`, Environment=`false` разрешает запросить ручное подтверждение задания, но **после подтверждения проверка завершится отказом без БД**. Если предварительный флаг репозитория отсутствует/выключен, задания Environment вообще не планируются к выполнению. При текущем запрете ничего включать не требуется.

### Защита от подстановки переменной другого уровня

`vars` объединяет несколько уровней и сам по себе не показывает происхождение значения. Простое переименование Repository-флага не защищало бы от оставшейся Repository-копии старого Environment-флага или SHA. Поэтому `migration_entry` заранее требует **пустые** значения `vars.ORBITA_CLOUD_MIGRATIONS_ENABLED` и `vars.ORBITA_ALLOWED_MIGRATION_SHA` вне Environment. Любое непустое значение, даже `false`, означает ошибку конфигурации и блокирует защищённое задание.

Внутренний gate получает доказательство предварительной проверки из `needs.migration_entry.outputs`, а не повторно читает Repository-флаг в контексте Environment. Environment-параметры передаются только в шаг gate; они не вынесены в `env` всего workflow или job. Это устраняет зависимость от раннего вычисления и от одноимённых значений разных уровней. Во время согласованного окна настройки не меняются параллельно: предварительная проверка — наблюдение конфигурации этого запуска, не блокировка административных изменений GitHub.

Дополнительный токен для чтения переменных через API не нужен. Не добавлены permissions, секреты или обход ручного допуска. Отказ API проверки защит по-прежнему закрывает доступ.
