## 2. Уточнения к прежним документам

1. Полное ТЗ разрешает готовить авторизацию независимо от оформления расширенной серии API. Формальная приёмка 0.5.3 остаётся отдельной незавершённой контрольной точкой. Сообщение владельца о дополнительных успешных Wi-Fi/Yota-проверках сохранено без выдуманных количеств и дат.
2. Роль по умолчанию **отсутствует**. Auth-пользователь, профиль и роль — разные состояния. Создание пользователя Auth ничего не назначает и не создаёт автоматически.
3. Полная блокировка аккаунта закрывает защищённый доступ любой роли. Это **отдельный механизм** от будущего ограничения получения новых заказов водителем. Согласованное правило завершения уже принятой поездки при водительском ограничении сохраняется для этапа заказов; поездок в 3Б нет.
4. Доверенный администратор SQL и прикладная роль `admin` различаются. Обычный Android/HTTP-клиент с ролью `admin` не получает административных прав PostgreSQL.

## 3. Миграция и порядок применения

Одна версионная миграция: [202611050001_stage3b_auth.sql](../supabase/migrations/202611050001_stage3b_auth.sql).

Она выполняется в одной транзакции и:

1. Проверяет наличие `auth.users`/`auth.uid()`, выполнение от `postgres`, отсутствие опасных клиентских атрибутов/членства и существующих одноимённых объектов. При обнаружении объектов останавливается, не перезаписывая их.
2. Создаёт четыре публичные таблицы, закрытую служебную схему и строку блокировки конкурентных изменений.
3. Включает RLS, явно отзывает широкие права, создаёт две узкие политики профиля.
4. Создаёт проверку текущего собственного доступа, закрытые административные операции и триггеры защиты/аудита.
5. Явно закрывает административные функции для `PUBLIC`, `anon`, `authenticated` и, при наличии, `service_role`. Служебная схема не предназначена для списка exposed schemas API.

Повторное выполнение намеренно завершается ошибкой предварительной проверки. Это не сценарий обновления уже занятой схемы. SQL не содержит Project Ref и не умеет надёжно определять проект по названию базы; ручная сверка Dashboard обязательна. Нет команд применения через облачный CLI.

## 4. Таблицы, ограничения и RLS

RLS — правила базы, определяющие, какие строки видит и меняет пользователь. GRANT/REVOKE — отдельные разрешения на сами операции. Внешний ключ (FK) связывает записи и предотвращает ссылки на несуществующего пользователя. Оба уровня доступа нужны одновременно.

| Объект | Содержимое и защита |
|---|---|
| `public.orbita_profiles` | UUID Auth, отображаемое имя до 80 символов, время создания. Ни роли, ни блокировки. UUID уникален и связан с Auth через FK/CASCADE. |
| `public.orbita_user_roles` | UUID профиля — первичный ключ; одна роль `passenger`/`driver`/`admin`. Нет записи — нет роли. CHECK отклоняет неизвестное значение. FK к профилю. |
| `public.orbita_account_access` | UUID профиля, независимый `is_blocked`, положительная версия доступа. Таблица нужна для блокировки пользователя без роли и отделения полномочий от редактируемого профиля. |
| `public.orbita_access_audit` | Номер, UUID цели, операция, старые/новые роль или блокировка, время, заявленный оператор, признак его достоверности, действительная SQL-роль, источник и причина. UUID цели без FK: история остаётся после удаления аккаунта. |
| `orbita_mobile_private.access_mutex` | Одна служебная строка. Каждое изменение доступа записывает её, сериализуя административные операции. Клиентских прав нет. |

Индексы: первичные ключи, частичный индекс администраторов, история аудита по цели/времени. Паролей, токенов, email и копий имени в аудите нет. Причина ограничена 5–200 символами; оператор должен вводить только объяснение без секретов. Проверка известных маркеров не является универсальным детектором конфиденциальных данных.

`authenticated` получает SELECT собственного профиля и UPDATE **только `display_name`**. Две политики RLS требуют совпадения UUID с `auth.uid()` и актуального состояния `active`. Отсутствие профиля, роли, состояния блокировки или неизвестное состояние закрывает доступ. Заблокированный пользователь профиль не читает/не меняет.

У `anon` доступа к профилям нет. На ролях, блокировках и аудите нет клиентских разрешающих политик и базовых прав записи/чтения. У `service_role` права на новые административные объекты также отозваны. SQL-привилегии и RLS проверяются независимо. RLS не FORCE: доверенные функции-владельцы читают служебные данные намеренно; обычные клиенты таблицами не владеют и не имеют BYPASSRLS.

## 5. Функции и триггеры

Единственный клиентский RPC — **`public.orbita_get_access()`**, без аргумента пользователя. Он читает текущий `auth.uid()` и связанные таблицы в одном снимке, возвращает только собственные UUID, состояние, роль, версию и разрешённое отображаемое имя. Метаданные/JWT-клеймы роли не используются. EXECUTE есть только у `authenticated`; функция не назначает и не отзывает роли. Нейтральный ответ при блокировке/отсутствии роли нужен для экрана ожидания и не даёт рабочих полномочий.

Все функции принадлежат `postgres`, работают с `SECURITY DEFINER` (права доверенного владельца) и пустым `search_path` (без поиска подменённых объектов); обращения к таблицам квалифицированы схемой. Поэтому особенно важен запрет клиентского вызова административных функций. Закрытые функции:

- `lock_access()` — записываемая строка общей блокировки.
- `active_admins(uuid)` — число действующих администраторов, при необходимости без цели.
- `guard_access()` — неизменяемость UUID и защита последнего администратора.
- `audit_change()` — минимальный аудит и версия доступа.
- `protect_audit()` — запрет изменения/удаления аудита.
- `deny_truncate()` — защита от случайной массовой очистки доступа.
- `admin_access(...)` — доверенная операция над одним точным Auth UUID.

Прямого EXECUTE этих функций нет у клиентских ролей, включая прикладного администратора. Отзыв прав дополнен закрытой схемой, отсутствием административного RPC и отсутствием клиентских путей записи в защищённые таблицы.

Триггеры: три проверки доступа на профиле/ролях/блокировках; защита перед удалением Auth-пользователя; три записи аудита; защита самого аудита; три запрета TRUNCATE. Триггера регистрации с автоматической ролью нет. Удаление обычного Auth-пользователя каскадно удаляет прикладные строки, сохраняя аудит; удаление последнего действующего администратора отклоняется.

## 6. Доверенные административные операции

[Каталог шаблонов](../supabase/admin) предназначен только для будущего ручного SQL Editor. В шаблонах нет действительных пользовательских UUID или секретов; заглушка UUID останавливает случайное выполнение.

| Шаблон/операция | Предварительное условие и результат |
|---|---|
| [01_provision_profile.sql](../supabase/admin/01_provision_profile.sql), `provision` | Auth-пользователь уже существует. Создаются профиль и состояние доступа, **без роли**. Повтор не перезаписывает профиль. |
| [02_bootstrap_admin.sql](../supabase/admin/02_bootstrap_admin.sql), `bootstrap` | Профиль готов, аккаунт не заблокирован, действующих администраторов нет; требуется явное подтверждение. Назначает первого администратора доверенным SQL-путём. |
| [03_change_access.sql](../supabase/admin/03_change_access.sql), `assign` | Назначает `passenger`, `driver` или `admin`, атомарно заменяя прежнюю единственную роль. |
| Тот же шаблон, `revoke` | Удаляет только роль, не пользователя/профиль и не аудит. |
| Тот же шаблон, `block`/`unblock` | Меняет независимую блокировку. Разблокировка не назначает отсутствующую роль. |

После bootstrap обычные изменения требуют наличия хотя бы одного действующего администратора. Опасная потеря прав администратора и заявленное изменение собственных прав требуют `p_confirm_loss=true`. Это подтверждение не отменяет запрет отключения последнего администратора.

Успешная операция транзакционна, возвращает JSON с точной целью/результатом и оставляет аудит; повтор без изменения также отмечается. Отказ откатывает всю транзакцию, поэтому отдельная запись о неуспешной попытке в таблице не сохраняется; ошибки видны оператору/в результатах тестов. Не обещается независимый журнал всех отказов.

`p_operator` — **указанный вручную UUID**, не удостоверенная личность; `initiator_verified=false`. `database_actor=session_user` достоверно фиксирует роль соединения, а не человека за SQL Editor. Приложение не может само назначить себе оператора/роль.

### Последний администратор и конкуренция

Блокировка общей **записываемой** строки нужна и для REPEATABLE READ: две параллельные операции не могут обе воспользоваться старым числом администраторов. После ожидания в READ COMMITTED вторая видит новый результат, а при конфликте снимков REPEATABLE READ получает `40001`. Защита последнего администратора возвращает `23514`. Ошибку сериализации нельзя трактовать как успешное выполнение: оператор повторяет обследование состояния.

Аварийного флага «игнорировать последнего администратора» нет. Если данные испорчены доверенным обходом и действующих администраторов уже ноль, отдельный bootstrap возможен после расследования, резервирования, согласования и с аудитом. Суперпользователь и владелец объектов технически могут отключить триггеры/изменить DDL. Защита не гарантирует доступ к потерянной учётной записи, почте, SQL Editor и не контролирует внешнюю блокировку средствами Auth; эти действия требуют отдельной процедуры.

## 7. Flutter: вход, сессия и актуальные права

[Код авторизации](../apps/orbita_mobile/lib/src/auth), [экран](../apps/orbita_mobile/lib/src/screens/auth_screen.dart).

- Закреплены `supabase_flutter 2.18.3`, `flutter_secure_storage 11.2.0`, `http 1.6.0`; транзитивные версии — в lock-файле. minSdk остаётся 24.
- Используется SDK `SupabaseClient`, экспортированный `supabase_flutter`. Глобальный `Supabase.initialize` не вызывается: исключены скрытое фоновое восстановление, обработка входящих Auth-ссылок и запись в стандартные SharedPreferences.
- Явный `SecureAuthStorage` реализует актуальный `LocalStorage`. Репозиторий сам ожидает чтение/запись в Android secure storage, отделяя ключ по Ref окружения. Записи/очистка упорядочены, чтобы старый write не восстановил сессию после выхода. Роль на диск не записывается.
- Вход — email/пароль; регистрации, anonymous login, OAuth/OTP и восстановления пароля на этом этапе нет. Пароль не сохраняется и очищается из поля при отправке.
- Сохранённая сессия восстанавливается; истёкшая обновляется **явным `refreshSession(refreshToken)`**. Проверено по исходникам GoTrue 2.27.3: `recoverSession` с `autoRefreshToken=false` сам её не обновляет. Автообновление отключено, порядок контролирует приложение.
- После входа/восстановления и возвращения из фона запрашивается серверная роль. В активном приложении повтор — примерно каждые 30 секунд и не позже срока сессии. Это не мгновенное оповещение об отзыве.
- Пока идёт проверка, при ошибке сети, отзыве или блокировке прежний рабочий интерфейс закрыт. Поколения запросов, закрытие сокетов, отмена `RoleWorkLease` и пересоздание экрана исключают повторное открытие старой роли поздним ответом. Контракт отмены будущей работы требует подключения её реального I/O; сам по себе он не отменяет произвольный внешний процесс.
- Пассажир/водитель попадают только в интерфейс своей подтверждённой роли. Карты/заказы в нём по-прежнему не подключены. Администратор, отсутствие/отзыв/неизвестная роль, блокировка, отсутствующий профиль и неконсистентность получают нейтральные экраны.
- Общая проверка входа/восстановления/роли ограничена 12 секундами. Отдельный транспорт ограничивает полный HTTP-ответ 12 секундами и 1 МиБ, разрешает только ожидаемый HTTPS-хост, не следует перенаправлениям, сохраняет TLS-проверку.
- UI получает только безопасные коды ошибок/HTTP-статус, не исходные Auth-ответы. Состояния сети/TLS/таймаута, неверных данных, лимита попыток, сервера, сессии и непроверенных полномочий различаются. Пауза Supabase не угадывается.
- Временная сетевая/серверная ошибка не вызывает удаление secure session. Подтверждённо недействительный refresh обрабатывается отдельно. Выход удаляет локальную сессию; отзыв текущего refresh на сервере — ограниченная попытка. Выход всех устройств и мгновенное прекращение уже выданного JWT не обещаются.

Источник реальных прав для **каждой** защищённой операции — сервер. Просмотр принятого демонстрационного интерфейса остаётся отдельно помеченным просмотром с отключёнными рабочими действиями и не заменяет вход. Диагностика 0.5.3, уведомления и служба GPS сохранены; уход со страницы не останавливает диагностическую службу.

Официальные источники: [вход](https://supabase.com/docs/reference/dart/auth-signinwithpassword), [инициализация/LocalStorage](https://supabase.com/docs/reference/dart/initializing), [коды Auth](https://supabase.com/docs/guides/auth/debugging/error-codes), [опубликованный SDK](https://pub.dev/packages/supabase_flutter/versions/2.18.3), [secure storage](https://pub.dev/packages/flutter_secure_storage/versions/11.2.0). Проверялись также опубликованные исходники методов SDK, а не только примеры.

## 8. Проверки и их фактические пределы

### Локальная SQL-интеграция

[Тесты](../supabase/tests/test_auth_sql.py), [минимальная модель Auth](../supabase/tests/bootstrap_local.sql), [инструкция](../supabase/README.md).

**17 тестовых сценариев прошли**, JSON-отчёт содержит **89 проверок/контролей**, на настоящей PostgreSQL 17 в одноразовом Docker `--network none`, без опубликованных портов, с закреплённым образом. Это применение миграции к локальной базе, не статический анализ.

Клиентские запросы выполняются отдельными соединениями **LOGIN `anon`/`authenticated`**, без SET ROLE владельца. Перед сценарием проверяются `current_user=session_user`, `rolsuper=false`, `rolbypassrls=false`, отсутствие владения таблицей и `auth.uid()`. Несколько вымышленных UUID имеют разные роли и состояния.

| Механизм | Проверки и результаты |
|---|---|
| GRANT/REVOKE | `anon` не читает профили/RPC; `authenticated` не пишет роли, блокировки и аудит. Проверены реальные SQL-ошибки и неизменность строк. |
| RLS | Своё чтение и изменение имени проходят; чужие строки скрыты, чужой UPDATE возвращает ноль. Отсутствие роли/блокировка/отзыв закрывают профиль. |
| Отдельное достижение RLS | Только в одноразовой БД временные GRANT позволяют дойти до политик ролей/блокировок/аудита: SELECT/UPDATE/DELETE возвращают ноль, INSERT отклонён именно сообщением row-level security. Эти GRANT не входят в миграцию. |
| Административные контроли | Те же корректные записи SELECT/UPDATE/INSERT доступны `postgres`; проверки в транзакции откатываются. Они отмечены как административные, не как RLS. Неизменяемость аудита проверяется отдельным триггерным запретом и для владельца. |
| Функции | Закрытая схема, EXECUTE, владелец и пустой search_path; прикладной `admin` остаётся SQL-клиентом без административного вызова. Проверены широкие default grants и отдельный `service_role`. |
| Ограничения/входные данные | CHECK/FK/уникальность/ошибочный UUID/неподготовленный профиль различаются по SQLSTATE и не выдаются за RLS. |
| Жизненный цикл | Нет автоматической роли, назначение/смена/отзыв/блокировка/разблокировка, удаление с сохранением аудита, отсутствующий профиль/состояние, отказ повторной миграции. |
| Последний администратор | Отзыв, понижение, блокировка, удаление профиля/Auth и массовая очистка отклоняются; два конкурирующих изменения сохраняют одного действующего администратора в READ COMMITTED и REPEATABLE READ. |
| Конкурентный отзыв клиентских прав | Изменение своего профиля, начавшееся до блокировки, ждёт mutex, повторно проверяет текущие права на сервере и отклоняется после её COMMIT. Это отдельный серверный guard, не выдаётся за отказ GRANT/RLS. |

JSON-отчёт сохраняет действительную роль/UID, операцию, ожидаемые и фактические строки/ошибки, механизм и результат; административные контроли выделены. Тестовая `auth.uid()` читает GUC: **подпись JWT, PostgREST, Auth HTTP, почта и реальные настройки Supabase не проверяются**.

## 9. Риски, остановка и восстановление

- Облачная схема не обследована текущим агентом запросами к проекту. Перед применением владелец получает актуальные определения/права затрагиваемых объектов и проверяет, что новый проект действительно пуст относительно этой миграции. Любое совпадение имён — остановка и новый план.
- Модель `auth.uid()` не заменяет проверку подписанного JWT реальным PostgREST. Ошибки прав в настоящем облаке могут потребовать отдельной корректирующей миграции.
- Владельцу SQL Editor доступны обходы прикладных защит. Ввод ручного оператора не доказывает его личность. Пока нет защищённой веб-панели, мониторинга отказов, независимого хранения аудита и аварийного ответственного.
- Устройство/SDK и последующая смена ключей шифрования могут влиять на secure storage; реальные испытания обязательны. Смена debug-подписи может потребовать удаления старой **тестовой** установки с потерей её локальных данных/разрешений, только после отдельной инструкции.
- Закрытие клиентского запроса не доказывает, что сервер не успел создать сессию. Сетевой выход не даёт гарантии отзыва всех токенов; серверная проверка роли/блокировки остаётся обязательной для каждой рабочей операции.
- [Supabase Free](SUPABASE_FREE_RELIABILITY.md) может приостанавливаться при низкой активности за семь дней. Наблюдаемый таймаут не доказывает паузу. Для коммерческого такси рабочее размещение, регион хранения, резервирование и расходы согласуются отдельно. Тариф не менялся.

**До применения:** согласовать точную цель, сохранить определения и резервную копию, проверить возможность восстановления. При ошибке внутри миграции транзакция откатывается целиком. Никакой команды «удалить всё и повторить» нет.

**После COMMIT при обнаружении проблемы:** остановить испытания/запись, закрыть клиентский доступ согласованным отзывом прав или исправляющей миграцией, сохранить аудит и копию данных, выяснить причину. Восстанавливать доступ новой версионной поправкой; первоначальное состояние/резервную копию восстанавливать только отдельным планом. Не удалять таблицы, пользователей или аудит как обычный откат. Блокировка доступа не должна уничтожать сессии/данные без отдельной необходимости.

## 10. План облачного применения — только после отдельных разрешений

Это план будущих действий, **сейчас выполнять его не требуется**. В чате каждый ручной шаг выдаётся отдельно.

| Шаг | Кто и условия | Проверка/остановка |
|---|---|---|
| 1. Сверить проект | Владелец вручную подтверждает название и точный Ref выше. | Несовпадение — остановка до любого SQL. |
| 2. Обследовать без записи | Владелец либо автоматизация отдельно разрешённых read-only запросов. | Актуальная схема, владельцы, ACL, exposed schemas, резервирование; без реальных строк пользователей. |
| 3. Проверить Auth | Владелец вручную смотрит email/password, запрет публичной регистрации и anonymous login, подтверждение email и лимиты. | Любое изменение настройки требует отдельного согласия; пароли/ключи в чат не передаются. |
| 4. Применить миграцию | Владелец SQL Editor либо автоматизация только после явного разрешения именно этого файла и Ref. | Одна транзакция; при ошибке не продолжать следующими скриптами. |
| 5. Проверить структуру | Разрешённая read-only проверка таблиц, RLS, функций, ACL, владельцев, триггеров и отсутствия роли по умолчанию. | Любая лишняя привилегия — остановка. |
| 6. Создать вымышленные аккаунты | Владелец вручную в Dashboard после отдельного разрешения. | Для каждой роли, без роли, блокировки, второго администратора; уникальные пароли только у владельца. |
| 7. Подготовить профили/роли | Владелец запускает проверенный шаблон над одним UUID после отдельного разрешения. Сначала provision без роли, затем первый admin, второй admin, остальные роли. | Результат и аудит; опасные операции проверяются отдельно. Нельзя автоматически назначать роль новому Auth-пользователю. |
| 8. Проверить настоящий RLS | Отдельно согласованные клиентские запросы с настоящими Auth-сессиями, не ключом администратора. | Свой/чужой доступ, отказ записи ролей/блокировки/аудита и вызова admin; отдельно контроль SQL Editor. |
| 9. Испытать Android | Владелец на Tecno получает подходящий тестовый APK после отдельного шага. | Вход/выход/холодный запуск/refresh/сеть/фон/смена и отзыв роли/блокировка/крупный шрифт; без секретов в отчётах. |
| 10. Зафиксировать приёмку | Владелец подтверждает результаты, отдельно прикладывается серия API 0.5.3. | До этого этап 3Б и облачная интеграция не объявляются завершёнными. Этапы 3В/4 не начинаются автоматически. |

## 11. Что готово и что требует решения

**Подготовлено:** схема/миграция, частные административные SQL-шаблоны, RLS/ACL, аудит и конкурентная защита, Flutter AuthRepository/SDK/secure adapter/роль/нейтральные экраны, изолированные тесты, CI и шаблон физического отчёта.

**Проверено:** 17 SQL-сценариев/89 записей проверок, 175 искусственных Flutter-тестов, 19 Android-тестов, анализ и сборка в объёме раздела 8. Результат CI указывается отдельно по фактическому запуску.

**Не проверено:** реальные облачные миграции и права, настоящая авторизация/хранилище/refresh на телефоне, расширенная формальная серия 0.5.3, длительные GPS-прогоны.

**Нужно отдельное разрешение:** каждое облачное применение SQL, изменение Auth, создание аккаунтов/назначение ролей; перед ним точный Project Ref и конкретный объём.

**Предстоит выбрать:** кто отвечает за резервирование и аварийное восстановление, кто станет первым/вторым тестовым администратором, политика подтверждения email для вымышленных аккаунтов, будущее рабочее размещение и коммерческая подпись. Настоящие данные/пароли сюда не вписываются.

**На этой контрольной точке работа останавливается для чтения пакета владельцем. Само «продолжай» не разрешает облачные изменения.**
