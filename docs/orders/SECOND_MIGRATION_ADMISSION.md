## Точный состав будущего SQL

Одна таблица `public.orbita_orders`: первичный ключ `id`, внешний ключ пассажира
на `orbita_profiles(user_id)`, уникальность `(passenger_id, request_id)`, проверки
формата адресных точек, разных координат, статуса, отмены, версии и срока 5 минут.
Два индекса создаются ограничениями PRIMARY KEY/UNIQUE; третий — частичный
уникальный `orbita_orders_one_created_per_passenger` для `status='created'`.
Включается RLS без разрешающих клиентских политик.

Четыре публичных RPC, все возвращают `jsonb`:

- `public.orbita_create_order(uuid, jsonb, jsonb)`;
- `public.orbita_get_current_order()`;
- `public.orbita_get_order(uuid)`;
- `public.orbita_cancel_order(uuid)`.

Три закрытые функции:

- `orbita_mobile_private.order_point(jsonb) → jsonb`;
- `orbita_mobile_private.order_session_uid() → uuid`;
- `orbita_mobile_private.order_envelope(public.orbita_orders, timestamptz) → jsonb`.

Таблица недоступна клиентам напрямую; EXECUTE четырёх RPC выдан только
`authenticated`. Права PUBLIC/anon и прямые права service_role отозваны; закрытые
помощники клиентам недоступны. Функции SECURITY DEFINER закрепляют пустой
`search_path`. Новое создание проверяет серверную роль пассажира и блокировку
после общего mutex; собственные чтение/replay/отмена сохраняются после отзыва
роли. UID, срок JWT и существующая действующая `auth.sessions` проверяются;
роль из `user_metadata` прав не даёт. Подпись JWT проверяет доверенный Auth/PostgREST,
локальная SQL-проверка её не заменяет. Нет цены, водительской очереди, Push,
cron, новых аккаунтов, серверных ролей или изменений старых Auth-функций.

## Будущий read-only preview — только после отдельного разрешения

1. Сверить согласованный полный SHA коммита, оба SQL-хеша, единственный runnable
   файл первой миграции, проект/запрещённый ref и чистый checkout. Проверить
   фактическое одобрение владельцем именно этого запуска.
2. Через Session pooler с `sslmode=verify-full`, доверенным CA и паролем вне URL
   выполнить только SELECT в явных READ ONLY-транзакциях. Не запускать облачный
   CLI или SQL кандидата в облаке. Проверить единственную исходную историю,
   её текст/SHA, определения первой схемы, зависимости, GRANT/RLS/триггеры,
   ограничения клиентских ролей и отсутствие объектов второй миграции.
3. Вычислить отпечаток схемы и данных. Экспортировать `auth`, `public`,
   `orbita_mobile_private`, `supabase_migrations` с владельцами/ACL. Сверить
   состояние до/после, при любом изменении завершить отказом.
4. Зашифровать dump и манифест AES-256 в `snapshot.tar.gpg` независимой фразой
   не короче 24 символов. Проверить SHA-256, расшифровку, состав архива и SHA dump.
   Открытый dump и манифест не публикуются. Шифрованный архив содержит данные Auth,
   включая credential/session-строки: доступ и срок хранения требуют контроля.
5. В одноразовом контейнере фиксированной PostgreSQL с `--network none`
   восстановить снимок, имена владельцев и эффективные ACL схем из манифеста.
   Сверить полное предусмотренное логическое состояние, затем исполнить
   фиксированный кандидат **только на восстановленной копии** и проверить
   сохранность Auth и точные две записи истории.
6. Сформировать квитанцию `preview_passed` с SHA коммита/SQL/состояния/архива,
   Project Ref и результатами restore/rehearsal. Ошибка любого шага закрывает
   допуск. Локальная Native-репетиция не может служить облачной квитанцией.

Пока фактическое состояние облака не читалось. Совместимость с ним не заявляется.
В частности, история Supabase может хранить `statements` иначе, а определения,
владельцы и зависимости могут отличаться от эталона. В этом случае preview
остановится: исправление истории или автоматическое ослабление lock запрещено.

## Условия отдельного будущего apply

Нужны ещё одно явное разрешение владельца и новое одобрение Environment именно
для `apply`, тот же SHA коммита/SQL, успешный preview того же workflow/SHA,
доступный проверенный шифрованный архив и его подтверждённый SHA. Актуальность
проверяется точным равенством отпечатка состояния preview и БД, затем повторно
внутри транзакции под блокировками. Изменившиеся данные, в том числе Auth,
означают отказ и необходимость нового отдельно разрешённого preview.

В одной транзакции: advisory lock, блокировки таблиц четырёх схем,
preflight→кандидат→одна новая запись истории→postflight→COMMIT. Первая миграция
не исполняется повторно. Проверки до COMMIT сверяют прежние Auth-объекты/данные,
новые определения/ACL и историю. Таймаут ожидания блокировки 5 секунд,
одного SQL-оператора 30 секунд, idle-in-transaction 15 секунд. Блокировки могут
кратковременно задержать запись Auth; нужна согласованная пауза активности.

Неизвестный исход, отмена или ошибка после начала записи запрещают автоматический
повтор/re-run/repair/reset. Любая предыдущая попытка apply блокирует следующую
автоматическую; отдельно разрешённый `inspect` только собирает состояние и сам
не возобновляет допуск. Автоматического обратного SQL в облаке нет.

## Что ещё потребуется настроить и проверить

Ничего из перечисленного сейчас не создавалось и не менялось:

- Отдельный Environment `orbita-mobile-test-orders-migrations`: ручной reviewer
  владельца, запрет admin bypass, одна точная рабочая ветка без wildcard/tag.
- Repository-флаг `ORBITA_ORDERS_REPO_ENABLED`; только внутри нового Environment:
  `ORBITA_ORDERS_CLOUD_ENABLED`, `ORBITA_ORDERS_ALLOWED_SHA`,
  `ORBITA_ORDERS_ALLOWED_OPERATION`. Их внешние дубли запрещены; разрешение
  `preview` не разрешает `apply`.
- В новом Environment — подтверждённые `SUPABASE_TEST_PROJECT_REF`,
  `SUPABASE_FORBIDDEN_PROJECT_REF`, доверенный `ORBITA_TEST_DB_CA_PEM` и Secrets
  `ORBITA_TEST_DB_PASSWORD`, `ORBITA_ORDERS_BACKUP_PASSPHRASE`. Пароли не передаются
  в чат и не включаются в исходники/квитанции. Старые флаги и Environment
  первой миграции остаются без изменений.
- Доступность workflow_dispatch после регистрации нового workflow в GitHub
  пока не проверена. GitHub может потребовать его наличие в default branch;
  отдельное согласованное размещение потребуется **до** запуска. Это задание
  не разрешает merge, изменение `main` или обход через старый workflow.
- Будущий Docker-путь восстановления и доступность защищённых ресурсов GitHub
  должны успешно пройти отдельную проверку. Здесь проверен Native PostgreSQL,
  а не запуск в инфраструктуре GitHub.

Копия ограничена четырьмя схемами. Не восстановлены пароли/членство кластерных
ролей, глобальные настройки, Storage-файлы и другие схемы. Не доказаны полное
восстановление Supabase, работоспособность GoTrue/PostgREST, подпись JWT и
HTTP-вход после облачной миграции. Каталожный отпечаток покрывает предусмотренные
отношения/функции/ACL/RLS/ограничения/индексы/триггеры; это не универсальный аудит
всех PostgreSQL-объектов (например, отдельные определения enum/domain).

**Следующий шаг:** владелец отдельно разрешает только предварительную облачную
проверку без записи для указанного коммита и `fjqghohhohgvwlmefdmo`, с согласованным
