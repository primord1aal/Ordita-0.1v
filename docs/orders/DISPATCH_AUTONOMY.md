# Автономная проверка сроков диспетчеризации

Локальное предложение `supabase/proposals/orbita_dispatch_autonomy.sql` добавляет закрытый вызов существующего `dispatch_tick()`. Он выполняется от имени роли задания и берёт ту же блокировку, что и клиентские команды. Занятая блокировка откладывает обработку до следующего прохода. Если срок ещё не истёк и новое предложение некому отправить, вызов пропускает запись ревизии. Клиентским и API-ролям выполнение закрыто.

Проверка эффекта в PostgreSQL использует искусственное перемещение сроков в прошлое. Пассажирские и водительские запросы прекращаются, после вызова закрытой функции проверяются изменение статуса заказа, следующее предложение и продвижение прежнего водителя ровно один раз. Срок ответа остаётся 25 секунд, а поиск ограничен пятью минутами от создания заказа. Сервер отклоняет запоздалые команды независимо от интервала проверки. Уборка истёкшего состояния может отстать на интервал и время конкурентной транзакции.

Отдельное предложение `supabase/proposals/orbita_dispatch_autonomy_schedule.sql` регистрирует `orbita-dispatch-tick` с интервалом пять секунд, `lock_timeout=500ms` и `statement_timeout=3s`. Повтор точного расписания сохраняет одну запись. Несовпадение параметров блокирует регистрацию. [Supabase Cron](https://supabase.com/docs/guides/cron)

В изолированной PostgreSQL 17.11 с пакетом `pg_cron` 1.6.4 прошли семь проверок. Планировщик завершил истёкший поиск без клиентского RPC, повторное включение сохранило одну запись, после снятия задания новых запусков не было.

Перед облачным включением получить отдельный допуск после Dispatch и Maps. Сверить проект `orbita-mobile-test`, версию `pg_cron`, роль задания, БД, период и SQL. После включения проверить `cron.job_run_details` и поездку при закрытых приложениях. Для остановки снять только согласованное задание и проверить завершение текущего запуска и отсутствие следующих.

```sql
select cron.unschedule(jobid)
from cron.job
where jobname = 'orbita-dispatch-tick'
  and username = current_user
  and database = current_database();
```

Облачное расписание и доставка Push ожидают отдельных допусков. Работа планировщика не продлевает действующую 15-секундную аренду линии водителя.

## Фоновые предложения водителю

`supabase/proposals/orbita_dispatch_push.sql` сохраняет закрытое событие в той же транзакции, что и предложение. Локальные сценарии проверяют откат, конкурентное получение, ограниченные повторы, потерю аренды исполнителя, сроки и доступ. Идентификатор события равен ID предложения. Доставка выполняется за пределами транзакции назначения. Ответ поставщика фиксирует приём отправки этим поставщиком, а принятие поездки подтверждает только диспетчерский RPC.

Для тестового пилота выбран RuStore Push. Тело содержит только `kind=driver_offer`, `offer_id` и `expires_at` в UTC. Исполнитель использует ID водителя только для выбора зарегистрированного устройства. Адреса, контакты и содержимое заказа не передаются. При открытии приложение сверяет предложение с текущим серверным состоянием авторизованного водителя. [RuStore Push API](https://www.rustore.ru/help/sdk/push-notifications/send-push-notifications)

Предложение SQL содержит закрытую привязку одного текущего устройства к действующей водительской сессии. Новая регистрация заменяет старую, а отзыв сессии исключает устройство из доставки. Закрытый Edge-исполнитель `orbita-driver-push` принимает только POST с `x-orbita-worker-key` и работает с `orbita-mobile-test`. Пакет до восьми событий получает из ограниченных RPC, отправляет вне транзакции назначения и подтверждает только собственную аренду. TTL ограничен оставшимся временем предложения. Нулевой TTL пропускается, поскольку RuStore трактует его как хранение четыре недели.

RPC `orbita_driver_heartbeat()` продлевает только существующую линию с живой 15-секундной арендой. Истёкшая аренда возвращает `false`, а повторный выход на линию выполняет сам водитель. RPC не меняет место в очереди и не отменяет принятую поездку.

Сборка с RuStore использует закреплённый SDK 7.6.1. После подтверждённого входа Flutter регистрирует токен устройства. После подтверждённого выхода на линию Android может запустить видимую службу `dataSync`. Она выполняет heartbeat примерно каждые четыре секунды, пока рабочий экран в фоне. При открытом экране серверный срок поддерживает обычный опрос приложения. При отказе сервера, длительной потере связи, завершении сессии или системном лимите службы новые заказы перестают поступать на эту линию. Текущий access token службы хранится в памяти. Канал «Предложения водителю» использует системный звук и проверяет дубликаты и срок до показа.

Сборка без `ORBITA_RUSTORE_PUSH_PROJECT_ID` компилируется и использует обычный рабочий экран со штатным опросом. Для физической проверки Push нужен APK с зарегистрированным в RuStore пакетом и сертификатом. [Интеграция RuStore SDK](https://www.rustore.ru/help/sdk/push-notifications/kotlin-java/7-6-1)

Для доставки в тестовом проекте требуются отдельные шаги.

1. Зарегистрировать Android-пакет и сертификат тестовой сборки в RuStore. В сборку передаётся публичный `ORBITA_RUSTORE_PUSH_PROJECT_ID`. Серверные `ORBITA_RUSTORE_PUSH_SERVICE_TOKEN` и `ORBITA_PUSH_WORKER_KEY` хранятся в защищённом хранилище тестового проекта.
2. После Maps Apply отдельно согласовать SQL и публикацию `orbita-driver-push`. Проверить серверные разрешения claim/finish и оставить авторизацию Edge. Закрытое расписание должно передавать действующий серверный bearer и отдельный `x-orbita-worker-key` из хранилища. Облачное расписание доставки пока не включено.
3. На физическом Android проверить доступность RuStore в фоне, разрешение, звук, доставку после сворачивания, длительную линию, смену токена, повторы, просрочку, смену аккаунта и переход к актуальному предложению. Открытие уведомления не принимает заказ.
