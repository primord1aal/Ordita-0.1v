# Первый заказ пассажира — контракт v1 и локальная подготовка

Дата: 13 ноября 2026 года, Asia/Novosibirsk. База приложения: `bacedff`, рабочая ветка `codex/orbita-flutter-design-integration`.

Владелец разрешил начать следующий блок после приёмки карты/GPS 0.5.9+11 и уточнил: **цену в этом блоке не указывать**. Цель — создать собственный заказ, восстановить его после перезапуска и отменить. Логотип водителя остаётся отдельной отложенной правкой.

## Границы готовности

Это контракт и проверяемая локальная подготовка серверной части и клиентских моделей. Облачная схема не изменена; новые RPC в действующем проекте ещё отсутствуют. Приложение 0.5.9 продолжает работать в принятом владельцем режиме с отключённой кнопкой заказа. Новый APK на этом шаге не выпускается.

Первый заказ хранит два адреса и две точки, владельца и серверное состояние. Тарифов, цены, платежей, линии, очереди, назначения водителя и Push здесь нет. Созданный тестовый заказ не означает, что водитель уведомлён или начался реальный поиск машины. Перед будущим подтверждением в тестовом APK будет явно указано: «Тестовый режим: водитель не вызывается».

## Проверенная исходная схема

Подключённый Supabase прочитан только по метаданным, в явной `READ ONLY`-транзакции с короткими таймаутами. Цель — **orbita-mobile-test**, ref `fjqghohhohgvwlmefdmo`, PostgreSQL 17.11.0.011. История содержит только `202611050001 / stage3b_auth`.

В `public` сейчас четыре таблицы: `orbita_profiles`, `orbita_account_access`, `orbita_user_roles`, `orbita_access_audit`. Таблиц заказов нет. Полномочия берутся из текущих таблиц роли/блокировки, а не пользовательской metadata. Продуктовые роли `passenger/driver/admin` отличаются от SQL-ролей `anon/authenticated/service_role`.

`orbita_get_access()` проверяет пользователя и текущие роль/доступ, но сам не проверяет `auth.sessions`, `session_id`, срок JWT или его отзыв. Поэтому новые операции заказов получают отдельный guard действующей сессии; прежний вход и RPC доступа не переписываются. Полная подпись JWT и HTTP/PostgREST проверяются на интеграционном этапе, а не объявляются проверенными моделью SQL claims.

Старый проект `orbita-dev` не читается и не изменяется. Не меняются аккаунты, роли, настройки Supabase, Secrets/Variables/Environment, workflows или принятая первая миграция.

## Правила заказа

1. Новый заказ создаёт только вошедший пассажир с текущим активным серверным доступом. Владелец берётся из `auth.uid()`; клиент не задаёт его параметром.
2. У пассажира одновременно один заказ в состоянии `created`, пока его серверный срок не истёк. Новый запрос при существующем активном заказе возвращает понятный конфликт, а не вторую машину.
3. Обе точки должны быть выбраны. Адрес — непустая короткая подпись, координаты хранятся отдельно; одинаковые начальная и конечная точки отклоняются. Ограничение зоны обслуживания здесь не придумывается.
4. На одно нажатие создаётся один `request_id`. Перед отправкой приложение должно сохранить этот ID и исходные параметры, затем повторять их до выяснения результата. Тайм-аут ответа не означает, что заказ не создался.
5. Один владелец + один `request_id` + те же нормализованные параметры возвращают тот же заказ, в том числе после отмены/истечения срока. Тот же ключ с другим содержимым даёт конфликт и ничего не перезаписывает. Изменённые параметры после неизвестного исхода нельзя отправлять под прежним ключом.
6. Сервер задаёт `created_at`, `expires_at = created_at + 5 минут`, ID и версию состояния. Повтор, восстановление и новая сессия срок не продлевают.
7. До появления водительского блока `created` означает только запись тестового заказа. В момент серверного deadline API уже считает его отменённым по `search_timeout`, даже если приложение закрыто и физическая строка ещё не нормализована. Истечение вычисляется сервером, не часами телефона.
8. Физическая нормализация истёкшей строки при следующем создании/отмене не меняет логическое время отмены или версию. Фоновый диспетчер, уведомления и проверка будущего принятия до deadline остаются отдельным блоком; нынешняя подготовка их не имитирует.
9. Пассажир отменяет свой `created` атомарно. Повтор отмены возвращает прежний результат. В момент deadline и позже сохраняется причина `search_timeout`, а не переписывается на `passenger`.
10. Доступ к собственному уже созданному заказу и его отмена до назначения сохраняются для действующей сессии после блокировки/смены роли. Создать новый заказ при этом нельзя. Правила принятой поездки из основного ТЗ сохраняются для следующего водительского блока; отмена уже принятой поездки этим API не разрешается автоматически.

| Состояние API | Что означает | Следующее действие |
|---|---|---|
| `created` | Собственный тестовый заказ записан, серверный deadline ещё не наступил | Читать или отменить |
| `cancelled`, причина `passenger` | Пассажир отменил до deadline | Можно создать новый заказ с новым ключом |
| `cancelled`, причина `search_timeout` | Серверный срок истёк | Можно создать новый заказ с новым ключом |

`get_current` возвращает действующий собственный заказ, если он есть; иначе последний собственный заказ, включая терминальный результат. `null` означает отсутствие истории. Наличие объекта само по себе не означает активный заказ: интерфейс обязан учитывать `status`.

## HTTP/RPC-граница

Все четыре функции доступны только через действующую пользовательскую сессию. Ответ: `{contract_version: 1, server_time: <UTC>, order: <object|null>}`. Клиент принимает `null` только для `get_current` и проверяет владельца и ожидаемый ID запроса/заказа до использования ответа.

| RPC | Параметры | Результат |
|---|---|---|
| `orbita_create_order` | `p_request_id: uuid`, `p_pickup: jsonb`, `p_destination: jsonb` | Квитанция нового либо того же ранее созданного заказа |
| `orbita_get_current_order` | Нет | Действующий/последний собственный заказ либо `null` |
| `orbita_get_order` | `p_order_id: uuid` | Собственный заказ |
| `orbita_cancel_order` | `p_order_id: uuid` | Авторитетный результат отмены/ранее завершившегося заказа |

Каждая точка имеет **ровно** поля `address`, `latitude`, `longitude`. Адрес ограничен 500 Unicode code points; координаты — конечные JSON numbers в диапазоне ±90/±180. Сначала набор whitespace U+0009…000D, 0020, 0085, 00A0, 1680, 2000…200A, 2028, 2029, 202F, 205F, 3000, FEFF заменяется на обычный пробел, затем удаляются крайние обычные пробелы. Нормализация одинакова в Dart и SQL и не зависит от locale.

Квитанция содержит `id`, `passenger_id`, `request_id`, `pickup`, `destination`, `status`, `cancellation_reason`, `created_at`, `expires_at`, `cancelled_at`, `version`. Время UTC с точностью до микросекунд. Для `created`: версия 1, причина/отмена пусты, `server_time < expires_at`. Для терминального состояния: версия 2; отмена пассажиром раньше deadline, отмена по сроку строго на `expires_at`. Неизвестная версия/состояние или чужой владелец не превращаются в успешный заказ на клиенте.

Ошибки содержат только фиксированный машинный код, без адресов, координат, UUID или внутренних данных. Коды: `ORB_ORDER_INVALID_REQUEST`, `ORB_ORDER_SESSION_REQUIRED`, `ORB_ORDER_CREATE_FORBIDDEN`, `ORB_ORDER_NOT_FOUND`, `ORB_ORDER_ACTIVE_EXISTS`, `ORB_ORDER_IDEMPOTENCY_CONFLICT`, `ORB_ORDER_STATE_CHANGED`. Чужой и отсутствующий ID неразличимы. Клиент показывает собственные русские сообщения, не сырой ответ БД.

## Минимальная схема и защита

Предлагаются одна таблица `public.orbita_orders`, ограничения/индексы владельца и ключа запроса, четыре публичных RPC и внутренние helpers в существующем private schema. У таблицы включён RLS; прямые чтение/INSERT/UPDATE/DELETE клиенту не выдаются. Доступ идёт через ограниченный API. Default grants отзываются явно, `PUBLIC` и `anon` не получают исполнение. Только нужные публичные RPC доступны `authenticated`.

Внутри привилегированной границы проверяются UID, наличие пользователя, `session_id → auth.sessions.id/user_id`, `not_after` при наличии и срок `exp`; чужая/отозванная сессия не принимается. Продуктовая роль проверяется по текущей БД после ожидания существующего mutex доступа. Mutation сериализуется с изменением блокировки/роли; проверки в интерфейсе не заменяют эту защиту. Привилегированная логика не берёт роль/владельца из аргументов, работает с фиксированным `search_path` и не обращается по HTTP из транзакции.

Перед облачной интеграцией дополнительно проверяются реальные PostgREST/JWT: отказ без подписи/сессии, корректная выдача `session_id`, истёкший JWT и отзыв сессии, поведение блокировки и безопасный HTTP-ответ. Модель `auth.jwt()` локального стенда этого не заменяет.

## Проверки

Критические серверные сценарии: GRANT отдельно от RLS; реальный LOGIN `anon/authenticated` без superuser/BYPASSRLS; чтение только своего; создание текущим пассажиром; блокировка/отзыв роли и гонка с mutex; строгие параметры; одинаковый replay; конфликт содержания; два конкурентных одинаковых ключа; два разных ключа при одном активном заказе; безопасная повторная отмена; граница пяти минут; восстановление терминального результата; проверка сессии и Unicode-нормализации.

Клиентские модели отдельно проверяют сериализацию стабильного запроса, версию/структуру квитанции, собственника, ожидаемый ID, координаты, UTC/хронологию и согласованность состояния. Runtime ещё не использует эти модели, поэтому они не включают кнопку заказа сами по себе.

Итоговые команды и результаты локального прогона записываются в [LOCAL_PREPARATION.md](LOCAL_PREPARATION.md). Успешные части прежнего набора Flutter не повторяются без изменения их runtime.

## Кандидат миграции и следующий допуск

Кандидат `20261112172442_passenger_orders.sql` создан официальным закреплённым CLI 3.0.0 и находится в `supabase/proposals/`, вне автоматически исполняемого каталога. Первая миграция/история/lock.json не меняются. Кандидат не означает разрешение на облачное применение.

Существующий защищённый исполнитель рассчитан на первую миграцию и пустую исходную историю. Для второй нужен отдельный ограниченный допуск с исходной историей `[202611050001]`, точным целевым ref, SHA кандидата, проверкой актуальной схемы и планом восстановления. Старые миграционные флаги/SHA и GitHub Environment автоматически не переиспользуются и сейчас не изменяются. Облачный Apply не запускается до готовности и согласования этого конкретного шага.

Сначала проверяется весь SQL в одной изолированной локальной транзакции. При неизвестном исходе облачной операции автоматический повтор/repair/reset запрещён. После возможного применения нового API выполняется отдельная проверка реальных RPC, затем подключение Flutter и APK. Рабочая инфраструктура в РФ и вход по СМС остаются отдельными решениями до запуска для реальных пассажиров.
