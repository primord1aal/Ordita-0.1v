# Тестовая диспетчерская

Клиент находится в `apps/orbita_admin/dist`. Он обращается к одному тестовому проекту по HTTPS. API-предложение `supabase/proposals/orbita_admin_read_model.sql` читает уже существующие заказы и очередь диспетчеризации. В облаке этот API ещё недоступен.

Клиент использует publishable key и сессию тестового администратора. Ключ клиента указывается в локальном `config.json` по примеру `config.example.json`. Токен живёт в памяти открытой вкладки. При выходе или запрете серверного чтения данные убираются с экрана. Разрешение на чтение проверяют текущая Auth-сессия и роль в серверных таблицах. Состояние вкладки или поле роли в JWT не дают права читать заказы.

Снимок возвращает до 50 активных заказов, 50 завершённых записей и 50 водителей. Очередь упорядочена теми же полями, что и подбор водителя. Адреса активных заказов видит администратор. Контакты, координаты и тела Auth-ответов в снимок не входят. Локальные проверки охватывают запреты пассажиру и водителю, блокировку администратора, отозванную сессию, порядок очереди и предел истории.

После успешного применения фиксированных миграций Dispatch и Maps потребуется отдельный проверяемый допуск к DDL панели. Порядок важен: предложение панели добавляет индекс истории, а Preview квоты карт сверяет исходный каталог. После применения к тестовой базе выставить в Data API только схему `orbita_admin_api`, оставив `orbita_admin_private` вне списка публичных схем. Перед выдачей панели проверить настоящий Auth и отказ HTTP для чужих ролей с вымышленными заказами.

Операции изменения доступа водителей, телефонный заказ и просмотр журнала действий остаются отдельными частями админ-панели. Прежние команды администратора по-прежнему работают по своему допуску.
