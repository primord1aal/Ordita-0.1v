## Точный состав

- `public.orbita_orders`: добавить nullable `driver_id` (FK на профиль) и `completed_at`; расширить ограничения допустимых состояний; три индекса для единственной активной поездки пассажира/водителя и очереди поиска. Исходные данные не обновляются при установке.
- Закрытая схема `orbita_mobile_private`: таблицы `dispatch_drivers` и `dispatch_offers`, последовательность `dispatch_queue`, индексы единственного предложения на заказ/водителя, RLS без клиентских политик, полный запрет прямого клиентского доступа.
- Закрытые функции `dispatch_allowed`, `dispatch_tick`, `dispatch_snapshot`. Новый публичный RPC `orbita_dispatch(text,jsonb)` доступен только `authenticated`; внутри проверяются живая сессия, серверная роль, принадлежность заказа/предложения и допустимый переход.
- Прежние Auth, роли, функции v1, их содержимое и контрольные суммы не изменяются. Нет создания аккаунтов, cron, Push, внешних HTTP, изменений Secrets/Variables/Environment.

Общий mutex объединяет диспетчеризацию, прежние создание/отмену и изменения доступа. Начальная проверка сверяет определения шести существующих функций с read-only Preview; несовпадение останавливает применение. Установка выполняется целиком в одной транзакции, повторный запуск отклоняется.

## Preview и проверки

Read-only запросы к указанному проекту подтвердили состояние исходной таблицы и определения используемых функций. Это ограниченная проверка затронутой схемы, не полный backup/восстановленный облачный снимок и не CLI dry-run. Облачные записи не выполнялись.

На локальной PostgreSQL 17.11: установка после двух прежних миграций, 15 сценариев диспетчеризации и 16 прежних сценариев заказов. Клиентские соединения — реальные LOGIN `authenticated`/`anon`, без BYPASSRLS, владельца или SET ROLE. Проверены очередь, чужой доступ, повторы, гонки и восстановление новым соединением. Время сроков проверено с искусственно состаренными тестовыми строками на настоящей БД; это не пяти-минутный физический прогон.

Подпись JWT, облачные Auth/PostgREST и устройства этими локальными проверками не подтверждены. Flutter-тесты используют искусственный API; результаты нельзя считать облачным сквозным тестом.

## Применение и восстановление

Перед Apply требуется отдельное разрешение владельца на точный SQL/SHA выше. Действующие защищённые migration workflows закреплены за прежними миграциями и другой веткой: их нельзя использовать для повторного Apply. Новый APK workflow только проверяет и собирает; базы он не меняет.

Порядок следующего шага: согласовать механизм Apply с владельцем, сохранить защищённую резервную копию в предусмотренном месте, подтвердить целевой Ref и соответствие исходной схемы, выполнить единственную транзакцию с новой записью истории, затем проверить каталог/ACL и работу RPC. Если для этого потребуются изменения допуска Environment, они также согласуются отдельно; в текущем пакете таких изменений нет.

Ошибка до COMMIT откатывает SQL. При неизвестном исходе сначала read-only проверка, без автоматического повтора/reset/repair. После успешного Apply автоматический downgrade не допускается: он удалил бы сведения о назначениях. При проблеме остановить новые заказы и подготовить отдельную корректирующую миграцию; восстановление из копии требует решения владельца с учётом появившихся данных.

После Apply владелец выполняет [тест двух телефонов](../ORBITA_0.6.0.md). До этого APK является подготовленной клиентской сборкой, а версия не считается принятой.

Защищённый исполнитель и точные изменения допуска подготовлены отдельно: [DISPATCH_060_ACCESS.md](DISPATCH_060_ACCESS.md). До отдельного разрешения настройки Environment не меняются.
